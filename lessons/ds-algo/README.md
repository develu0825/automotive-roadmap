# 자료구조 · 알고리즘

UART(시리얼 통신) 인터럽트가 1바이트씩 데이터를 쏟아낼 때, 메인 루프가 그 데이터를 처리하는 속도보다 데이터가 들어오는 속도가 빠르면 어떻게 해야 할까요. 데이터를 어딘가에 잠시 쌓아 두었다가 메인 루프가 여유 있을 때 꺼내 쓰는 구조가 필요합니다. CAN 버스에서 수백 개의 서로 다른 메시지 ID가 쏟아져 들어올 때, 내가 원하는 ID만 빠르게 걸러내려면 "들어온 순서대로 하나씩 비교"하는 방법보다 훨씬 빠른 방법이 필요합니다. 진단 코드(DTC, Diagnostic Trouble Code) 수백 개 중에서 특정 코드가 등록되어 있는지 확인할 때도 마찬가지입니다. 이런 모든 상황에서 "데이터를 어떤 모양으로 쌓아 두는가"와 "그 데이터를 다루는 절차를 어떻게 짜는가"가 프로그램의 성능과 안정성을 가릅니다. 이것이 자료구조(data structure)와 알고리즘(algorithm)입니다.

일반 데스크톱 프로그램이라면 "일단 되게만 만들고 느리면 나중에 고치자"는 접근이 가능하지만, 자동차 ECU는 그럴 수 없습니다. ECU는 보통 RAM이 수십 킬로바이트 수준이라 무한히 커지는 구조를 쓸 수 없고, 제동이나 조향처럼 안전과 직결된 기능은 "최악의 경우에도 몇 밀리초 안에 끝난다"는 보장이 있어야 합니다. 평균적으로는 빨라도 어쩌다 한 번 느려지는 알고리즘은, 그 "어쩌다 한 번"이 하필 긴급 제동 순간에 일어나면 그대로 사고로 이어질 수 있습니다. 그래서 자동차 임베디드 개발자는 "이 자료구조가 메모리를 얼마나 쓰는가"와 "이 알고리즘이 최악의 경우 얼마나 걸리는가"를 항상 함께 따져야 합니다.

이 레슨은 앞서 배운 C 언어의 포인터와 구조체를 바탕으로, 배열, 연결 리스트, 큐, 트리라는 기본 자료구조와, 이들의 성능을 비교하는 언어인 복잡도(complexity) 개념을 다룹니다. 수학적으로 어려운 증명보다는, "이 구조를 왜 쓰는가"와 "이 구조가 자동차 소프트웨어에서 어떤 모습으로 등장하는가"에 집중합니다.

## 학습 목표

- 복잡도(시간/공간, Big-O 표기)가 무엇을 의미하며 왜 "최악의 경우"가 자동차 소프트웨어에서 중요한지 설명할 수 있다.
- 배열과 연결 리스트의 메모리 구조 차이와 각각의 장단점을 실제 사례로 설명할 수 있다.
- 원형 버퍼(circular buffer)를 이용한 큐 구조로 인터럽트와 메인 루프 간 데이터 전달을 구현할 수 있다.
- 이진 탐색 트리의 탐색 원리와, 정렬된 데이터에서 이진 탐색이 왜 빠른지 설명할 수 있다.
- 정적 메모리만으로 자료구조를 구현해야 하는 임베디드 제약을 이해하고 적용할 수 있다.

## 복잡도: "빠르다"를 숫자로 말하기

두 개의 코드가 있는데 하나는 데이터 10개일 때 더 빠르고, 다른 하나는 데이터 10000개일 때 더 빠르다면, 둘 중 뭐가 "더 좋은 알고리즘"일까요. 이 질문에 답하려면 "입력 크기가 커질 때 걸리는 시간이 어떤 패턴으로 늘어나는가"를 봐야 합니다. 이를 표현하는 방법이 Big-O 표기법입니다. 예를 들어 배열에서 특정 값을 하나씩 비교해서 찾는 선형 탐색(linear search)은 데이터가 n개일 때 최악의 경우 n번 비교해야 하므로 O(n)이라고 씁니다. 정렬된 배열에서 절반씩 줄여가며 찾는 이진 탐색(binary search)은 O(log n)입니다. 데이터가 100만 개일 때, O(n)은 최악의 경우 100만 번 비교해야 하지만 O(log n)은 약 20번이면 충분합니다. 이 차이는 데이터가 커질수록 극적으로 벌어집니다.

여기서 꼭 짚어야 할 것은 "평균적으로 빠른 것"과 "최악의 경우에도 빠른 것"은 다른 이야기라는 점입니다. 어떤 알고리즘은 보통은 매우 빠르지만 특정 입력에서 갑자기 느려질 수 있습니다. 데스크톱 소프트웨어라면 이런 경우가 가끔 발생해도 사용자가 약간의 지연을 느끼는 정도로 끝나지만, 자동차 제어 소프트웨어에서는 "이 계산이 반드시 1밀리초 안에 끝난다"는 보장이 안전 요구사항 자체일 수 있습니다. 이렇게 "작업이 반드시 끝나야 하는 한계 시간" 안에서 끝남을 보장하는 것을 실시간 시스템(real-time system)의 핵심 과제라고 부르고, 그 한계 시간 내 가장 오래 걸리는 경우를 최악 실행 시간(WCET, Worst-Case Execution Time)이라고 합니다. 그래서 자동차 임베디드 개발자는 "이 알고리즘의 최악의 경우 복잡도가 무엇인가"를 거의 항상 확인합니다.

## 배열과 연결 리스트: 메모리 모양의 차이

앞서 배운 것처럼 배열(array)은 메모리에 같은 타입의 값들이 연속으로 붙어 있는 구조입니다. 이 덕분에 `arr[i]`로 몇 번째 원소든 즉시(O(1), 인덱스 계산 한 번으로) 접근할 수 있습니다. 반면 중간에 새 원소를 끼워 넣거나 빼려면, 그 뒤에 있는 모든 원소를 한 칸씩 밀거나 당겨야 하므로 O(n)이 걸립니다.

연결 리스트(linked list)는 각 원소(노드, node)가 자신의 값과 "다음 노드를 가리키는 포인터"를 함께 갖고, 노드들이 메모리 여기저기에 흩어져 존재하면서 포인터로 서로 연결된 구조입니다.

```c
typedef struct Node {
    int value;
    struct Node *next;
} Node;
```

연결 리스트는 중간에 노드를 끼워 넣거나 뺄 때 그 지점의 포인터만 바꾸면 되므로 O(1)이지만, "다섯 번째 노드가 뭐냐"를 알려면 처음부터 포인터를 다섯 번 따라가야 하므로 O(n)이 걸립니다. 즉 배열은 접근이 빠르고 삽입/삭제가 느리며, 연결 리스트는 그 반대입니다.

임베디드에서는 특히 연결 리스트를 조심해서 씁니다. 노드마다 동적 할당(`malloc`)이 필요한데, 앞서 C 레슨에서 배운 대로 동적 할당은 메모리 파편화와 예측 불가능한 실패를 일으킬 수 있어 안전 기준에서 피하는 경우가 많습니다. 그래서 실무에서는 "최대 몇 개까지 담을지"를 미리 정해 둔 고정 크기 배열로 리스트와 비슷한 효과를 내는 경우가 흔합니다.

## 큐와 원형 버퍼: 인터럽트와 메인 루프 사이의 다리

큐(queue)는 "먼저 들어온 것이 먼저 나가는(FIFO, First-In First-Out)" 구조입니다. UART로 1바이트씩 들어오는 데이터, CAN 메시지가 도착하는 순서, 센서 샘플이 쌓이는 순서처럼 "들어온 순서를 지켜서 처리해야 하는" 모든 상황에 큐가 쓰입니다.

임베디드에서 큐는 보통 원형 버퍼(circular buffer, ring buffer)라는 고정 크기 배열로 구현합니다. 배열의 앞뒤를 논리적으로 이어 붙여서, 끝에 도달하면 다시 처음으로 돌아가는 방식입니다.

```c
#define QUEUE_SIZE 32

typedef struct {
    uint8_t buf[QUEUE_SIZE];
    uint8_t head;   // 다음에 쓸 위치
    uint8_t tail;   // 다음에 읽을 위치
    uint8_t count;  // 현재 쌓인 개수
} RingBuffer;

void ring_push(RingBuffer *q, uint8_t byte) {
    if (q->count == QUEUE_SIZE) return;  // 가득 찼으면 버린다 (오버런 방지)
    q->buf[q->head] = byte;
    q->head = (q->head + 1) % QUEUE_SIZE;  // 끝에 도달하면 0으로 돌아간다
    q->count++;
}

uint8_t ring_pop(RingBuffer *q) {
    uint8_t v = q->buf[q->tail];
    q->tail = (q->tail + 1) % QUEUE_SIZE;
    q->count--;
    return v;
}
```

UART 수신 인터럽트 서비스 루틴(ISR)에서는 바이트가 도착할 때마다 `ring_push`를 호출해 빠르게 큐에 넣고 즉시 인터럽트를 빠져나오고, 메인 루프는 여유 있을 때 `ring_pop`으로 하나씩 꺼내 처리합니다. 이 구조의 장점은 명확합니다. 할당과 해제가 전혀 없는 고정 크기 메모리만 쓰고, push와 pop 모두 O(1)이며, 나머지 연산을 나눗셈 대신 비트마스킹으로 바꾸면(크기를 2의 거듭제곱으로 정해서 `% QUEUE_SIZE`를 `& (QUEUE_SIZE - 1)`로 바꾸는 식) 더 빠르게 만들 수도 있습니다. ISR과 메인 루프라는, 서로 다른 속도로 움직이는 두 실행 흐름을 안전하게 이어 주는 다리 역할을 큐가 담당합니다.

## 트리와 이진 탐색: 정렬된 데이터를 빠르게 찾기

DTC(진단 트러블 코드) 목록처럼 "정렬된 상태로 보관하고, 특정 값이 있는지 빠르게 확인해야 하는" 데이터에는 이진 탐색 트리(binary search tree, BST)가 적합합니다. 트리는 각 노드가 최대 두 개의 자식(왼쪽, 오른쪽)을 가지며, 왼쪽 자식은 항상 자신보다 작은 값, 오른쪽 자식은 항상 자신보다 큰 값이 되도록 구성합니다.

```c
typedef struct TreeNode {
    uint16_t dtcCode;
    struct TreeNode *left;
    struct TreeNode *right;
} TreeNode;

bool contains(TreeNode *node, uint16_t code) {
    if (node == NULL) return false;
    if (code == node->dtcCode) return true;
    if (code < node->dtcCode) return contains(node->left, code);
    return contains(node->right, code);
}
```

이 구조에서 탐색은 매 단계마다 비교해서 전체 범위를 절반씩 좁혀 나갑니다. 트리가 균형 잡혀 있다면(왼쪽과 오른쪽 가지의 높이가 비슷하다면) 탐색은 O(log n)이 됩니다. 노드 1000개짜리 트리라도 약 10번의 비교면 원하는 값이 있는지 확인할 수 있습니다. 이는 정렬된 배열에서 절반씩 좁혀가며 찾는 이진 탐색과 본질적으로 같은 원리입니다.

다만 트리에 값을 한쪽으로만 계속 넣으면(예를 들어 항상 증가하는 순서로만 삽입하면) 트리가 한쪽으로 치우쳐서 결국 연결 리스트와 같은 모양이 되어버리고, 이 경우 탐색이 O(n)으로 나빠집니다. 이런 최악의 경우를 막기 위해 스스로 균형을 맞추는 트리(AVL 트리, 레드-블랙 트리 등)가 존재하지만, 임베디드에서는 구조가 복잡하고 동적 할당이 필요한 경우가 많아, 차라리 데이터 개수가 정해져 있다면 정렬된 고정 배열에 이진 탐색을 쓰는 더 단순한 방법을 선호하는 경우도 흔합니다.

<details><summary><b>심화: WCET과 알고리즘 선택</b></summary>

실시간 시스템에서는 "평균적으로 빠른 알고리즘"보다 "최악의 경우에도 예측 가능한 알고리즘"을 선호하는 경향이 있다. 예를 들어 퀵 정렬(quick sort)은 평균적으로 O(n log n)으로 매우 빠르지만, 특정 입력 분포에서는 최악의 경우 O(n^2)까지 느려질 수 있다. 반면 병합 정렬(merge sort)은 추가 메모리가 더 필요하지만 항상 O(n log n)을 보장한다. 자동차 제어 소프트웨어의 스케줄링 가능성 분석(schedulability analysis)에서는 각 작업의 최악 실행 시간(WCET)을 정적으로 추정해서, 모든 작업이 주기 안에 끝날 수 있는지를 수학적으로 검증한다. 이런 분석을 어렵게 만드는 재귀, 가변 길이 반복, 동적 할당은 안전 필수(safety-critical) 코드에서 기피되는 경우가 많다.

</details>

<details><summary><b>심화: 메모리 풀과 고정 크기 할당자</b></summary>

연결 리스트나 트리를 쓰고 싶지만 `malloc`/`free`의 예측 불가능성은 피하고 싶을 때 쓰는 절충안이 메모리 풀(memory pool, 고정 크기 할당자)이다. 프로그램 시작 시점에 "노드 100개를 담을 수 있는 배열"을 미리 통째로 확보해 두고, 노드가 필요할 때마다 이 배열에서 하나를 꺼내 쓰고(비어 있는 칸을 가리키는 작은 연결 리스트로 관리), 다 쓰면 다시 풀에 돌려준다. 이렇게 하면 할당과 해제가 항상 O(1)이고, 전체 메모리 사용량이 처음부터 고정되어 예측 가능하며, 파편화도 일어나지 않는다. 다수의 자동차 소프트웨어 플랫폼과 RTOS(실시간 운영체제)가 이런 고정 크기 풀 할당자를 기본 메모리 관리 방식으로 제공한다.

</details>

**확인 문제.** 원형 버퍼로 만든 큐에서 `head`와 `tail`이 같은 값을 가리키는 상황이 "큐가 비어 있다"는 뜻일 수도 있고 "큐가 가득 찼다"는 뜻일 수도 있다. 위 예제 코드는 왜 이 모호함을 겪지 않는가.

<details><summary>답 보기</summary>

위 구현은 `head`와 `tail` 비교만으로 상태를 판단하지 않고, 별도의 `count` 필드로 현재 쌓인 개수를 직접 추적한다. `ring_push`는 `count == QUEUE_SIZE`일 때 가득 찬 것으로 판단하고, 비어 있는지는 `count == 0`으로 판단하면 된다(예제에는 생략했지만 `ring_pop` 호출 전에 확인해야 한다). 이렇게 별도 카운터를 두면 `head == tail`이 "비었다"와 "가득 찼다" 둘 다를 의미할 수 있는 모호함이 사라진다. 카운터를 쓰지 않는 대안으로는 버퍼 크기를 실제 저장 가능한 개수보다 하나 더 크게 잡아서 `head == tail`이 항상 "비었다"만을 의미하게 만드는 방법도 있다.

</details>

**확인 문제.** DTC 코드 1000개가 이미 정렬된 배열로 저장되어 있다. 특정 코드가 존재하는지 확인하는 가장 효율적인 방법은 무엇이며, 복잡도는 얼마인가.

이진 탐색(binary search)을 쓰면 된다. 배열의 중간 원소와 찾는 값을 비교해서, 찾는 값이 더 크면 오른쪽 절반만, 더 작으면 왼쪽 절반만 다시 살펴보는 방식으로 매 단계마다 탐색 범위를 절반으로 줄인다. 1000개 원소에서는 최악의 경우에도 약 10번의 비교(log2 1000 ≈ 10)로 답을 찾을 수 있어 복잡도는 O(log n)이다. 배열이 정렬되어 있지 않다면 이진 탐색을 쓸 수 없고 처음부터 끝까지 하나씩 비교하는 O(n) 선형 탐색만 가능하므로, "정렬된 상태를 유지한다"는 전제 자체가 빠른 탐색의 전제조건이다.

## 정리

- 복잡도는 입력 크기가 커질 때 연산 횟수가 늘어나는 패턴을 나타내며, 자동차 소프트웨어에서는 평균 속도보다 최악의 경우 복잡도가 더 중요한 경우가 많다.
- 배열은 접근이 빠르고(O(1)) 삽입/삭제가 느리며(O(n)), 연결 리스트는 그 반대의 트레이드오프를 가진다.
- 원형 버퍼로 만든 큐는 고정 크기 메모리만으로 O(1) 삽입/삭제를 제공해, 인터럽트와 메인 루프처럼 속도가 다른 두 실행 흐름을 잇는 표준적인 방법이다.
- 이진 탐색 트리와 이진 탐색은 정렬된 데이터에서 O(log n)의 빠른 탐색을 제공하지만, 임베디드에서는 동적 할당 없이 정렬된 고정 배열로 단순하게 구현하는 경우도 흔하다.
- 실시간 시스템의 WCET 보장이라는 목표 때문에, 자동차 임베디드 개발자는 자료구조와 알고리즘을 고를 때 항상 메모리 예측 가능성과 최악의 경우 시간을 함께 고려한다.

자료구조와 알고리즘은 단순히 "코딩 테스트를 위한 지식"이 아니라, 제한된 메모리와 엄격한 시간 제약 속에서 안전하게 동작하는 소프트웨어를 설계하는 실전 도구다. 이 레슨에서 다룬 복잡도 감각과 기본 구조들은 이후 MCU 구조, RTOS, 통신 프로토콜 레슨에서 계속 다시 등장한다.

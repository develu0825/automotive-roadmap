# 보드 브링업

지금까지의 레슨은 모두 "이미 잘 동작하는 보드"를 전제로 했다. 베어메탈 코드를 올리면 LED가 켜지고, U-Boot 프롬프트가 시리얼로 떠오르고, 커널이 디바이스 트리를 읽어 드라이버를 연결하는 과정 전부가 "전원을 넣으면 당연히 CPU가 정상적으로 깨어난다"는 가정 위에 있었다. 그런데 자동차 부품 회사에서 새로운 ECU를 설계할 때는 이 가정 자체가 아직 성립하지 않는 순간이 있다. 설계팀이 막 받은 시제품 보드(프로토타입)에 처음 전원을 넣는 순간, 그 보드가 제대로 동작할지조차 아무도 보장할 수 없다. 전원 레귤레이터의 배선이 미세하게 잘못되었거나, 클럭 발생기의 커패시터 값이 데이터시트와 조금 달라 발진이 불안정하거나, 수백 개의 핀 중 하나가 엉뚱한 기능으로 설정되어 있을 수 있다. 이 모든 것이 맞아 들어가야만 비로소 CPU가 "살아 있는" 상태가 되고, 그 이후에야 지금까지 배운 베어메탈, 부트로더, 커널 이야기가 의미를 갖기 시작한다. 이 가장 밑바닥의 단계, 전원도 클럭도 아직 보장되지 않은 새 하드웨어에 첫 생명을 불어넣는 작업을 보드 브링업(board bring-up)이라 부른다.

갓 태어난 신생아에게 산소 공급과 심장 박동이 먼저 확인되어야 그 다음에 걷기나 말하기를 가르칠 수 있는 것과 비슷하다. 전원이 제대로 공급되는지(호흡), 클럭이 안정적으로 발진하는지(심장 박동)가 확인되지 않은 보드에서는 어떤 소프트웨어를 올려도 의미가 없다. 보드 브링업은 바로 이 생명의 가장 기초적인 조건들, 즉 전원 시퀀스(power sequencing), 클럭 트리(clock tree), 핀 뮤잉(pin muxing)을 하나씩 검증하고 세워나가는 과정이다.

보드 브링업은 하드웨어 엔지니어와 소프트웨어 엔지니어가 가장 밀접하게 협업해야 하는 단계이기도 하다. 소프트웨어만으로는 보드가 왜 켜지지 않는지 알 수 없고, 하드웨어만으로는 레지스터 설정이 올바른지 알 수 없다. 오실로스코프로 전원 핀의 전압 파형을 눈으로 확인하고, JTAG 디버거로 CPU 레지스터 값을 한 줄씩 들여다보며, "지금 이 신호가 왜 예상한 모양이 아닌가"를 함께 추적해 나가는 것이 브링업의 일상이다. 이번 레슨에서는 전원 시퀀스, 클럭 트리, 핀 뮤잉이 각각 왜 필요하고 어떻게 설정하는지, 그리고 "아무것도 보장되지 않은" 새 보드에서 가장 먼저 확인하는 전형적인 브링업 절차를 살펴본다.

## 학습 목표

- 전원 시퀀스가 왜 필요한지와, 전원 레일(rail)을 정해진 순서와 타이밍으로 올려야 하는 이유를 설명할 수 있다.
- 클럭 트리의 개념과, 오실레이터와 PLL이 CPU와 각 주변장치에 필요한 클럭 주파수를 만들어내는 원리를 설명할 수 있다.
- 핀 뮤잉이 무엇이며, 하나의 물리적 핀이 여러 기능 중 하나로 소프트웨어적으로 지정되는 방식을 설명할 수 있다.
- 새 보드에서 전형적으로 거치는 브링업 절차(전원 확인, 클럭 확인, 최소 코드로 핀 토글)를 순서대로 설명할 수 있다.
- JTAG 디버거와 오실로스코프 같은 도구가 브링업 과정에서 각각 어떤 역할을 하는지 설명할 수 있다.

## 전원 시퀀스: 순서를 지키지 않으면 칩이 망가진다

현대 SoC는 하나의 전압만으로 동작하지 않는다. CPU 코어 내부 로직은 보통 1.0V에서 1.2V 사이의 낮은 전압으로 동작하고, 입출력 핀들은 1.8V나 3.3V처럼 더 높은 전압으로 동작하며, DRAM은 또 다른 전압(예: 1.1V)을 요구한다. 이렇게 여러 전압을 공급하는 각각의 회로를 전원 레일(power rail)이라 부른다. 문제는 이 레일들이 아무 순서로나 켜져도 되는 것이 아니라는 점이다. 많은 SoC는 "입출력 전압이 코어 전압보다 먼저 올라오면 안 된다" 또는 "두 전압이 올라오는 시간 차이가 몇 밀리초를 넘으면 안 된다"는 엄격한 순서와 타이밍 규칙을 데이터시트에 명시한다. 이 규칙을 지키지 않으면 칩 내부의 트랜지스터에 설계 범위를 넘는 전압 스트레스가 걸려, 최악의 경우 칩이 영구적으로 손상될 수도 있다.

이 순서를 실제로 관리하는 하드웨어가 전원 관리 IC(PMIC, Power Management IC)다. PMIC는 배터리나 외부 입력 전압을 받아 여러 레일로 변환하면서, 내부에 미리 프로그램된 순서에 따라 각 레일을 정해진 시간 간격으로 순차적으로 켠다. 보드 브링업의 첫 단계는 바로 이 전원 시퀀스가 설계대로 동작하는지를 오실로스코프로 직접 측정해 확인하는 일이다.

```
시간(ms)   VDD_CORE(1.1V)   VDD_IO(1.8V)   VDD_DDR(1.1V)
0           0V                0V             0V
2           1.1V 도달         0V             0V
4           1.1V              1.8V 도달      0V
6           1.1V              1.8V           1.1V 도달
```

위와 같은 순서표는 "코어 전압이 먼저 안정되고, 그다음 입출력 전압, 마지막으로 DRAM 전압이 올라온다"는 전형적인 순서를 보여준다. 이 측정값이 데이터시트가 요구하는 순서와 허용 시간 범위 안에 들어오는지 확인하는 것이 전원 시퀀스 검증의 핵심이다. 만약 설계 단계의 배선 실수로 두 레일이 동시에 켜지도록 되어 있다면, 이 단계에서 문제를 발견해 보드를 수정해야 한다.

## 클럭 트리: 하나의 발진기에서 여러 속도를 만들어내기

전원이 안정적으로 공급되었다고 해도, CPU는 아무 동작도 스스로 시작할 수 없다. CPU의 모든 명령 실행은 클럭(clock)이라는 일정한 주기로 똑딱거리는 전기 신호에 맞춰 한 단계씩 진행되기 때문이다. 보드에는 보통 수십 MHz짜리 수정 발진기(crystal oscillator)가 하나 달려 있는데, 이 발진기가 만들어내는 기본 주파수는 CPU 코어가 실제로 필요로 하는 1 GHz 이상의 속도에는 한참 못 미친다. 이 기본 주파수를 CPU, 각종 버스, 주변장치가 필요로 하는 다양한 주파수로 곱하거나 나눠주는 회로가 PLL(Phase-Locked Loop)이며, 이 PLL들이 체계적으로 연결되어 전체 칩에 클럭을 공급하는 구조를 클럭 트리(clock tree)라 부른다.

예를 들어 24 MHz 수정 발진기에서 출발해, CPU 코어용 PLL이 이를 50배로 곱해 1.2 GHz를 만들고, DDR 메모리 컨트롤러용 PLL이 다른 배율로 800 MHz를 만들고, UART 같은 저속 주변장치는 그보다 훨씬 느린 클럭을 그대로 나눠 쓰는 식이다. 브링업 단계에서는 이 클럭 트리를 설정하는 레지스터를 직접 써서, 각 PLL이 올바른 배율로 안정적으로 발진하는지(lock 상태가 되는지) 확인해야 한다.

```c
#define PLL_CORE_CTRL   (*(volatile uint32_t *)0x40030000UL)
#define PLL_CORE_STATUS (*(volatile uint32_t *)0x40030004UL)
#define PLL_LOCKED_BIT  (1u << 0)

void bringup_core_pll(void) {
    /* 입력 24MHz 기준, 배율 설정값을 레지스터에 기록 */
    PLL_CORE_CTRL = 0x00000032;  /* 배율 설정: 24MHz * 50 = 1.2GHz */

    /* PLL이 안정적으로 잠길(lock) 때까지 대기 */
    while (!(PLL_CORE_STATUS & PLL_LOCKED_BIT)) {
        /* lock 비트가 설 때까지 폴링 */
    }
}
```

이 코드는 베어메탈 레슨에서 배운 폴링 패턴, 즉 레지스터의 특정 비트가 설정되기를 기다리는 방식과 정확히 같은 모양이다. 브링업 단계에서는 아직 인터럽트 체계도, RTOS도, 커널도 올라가지 않은 가장 원초적인 상태이므로, 모든 확인 작업은 이렇게 단순한 레지스터 폴링 코드로 이루어진다. PLL이 lock 상태에 도달하지 못하면, 보통 수정 발진기 주변의 커패시터 값이 데이터시트의 권장값과 다르거나, 배율 설정 레지스터 값 자체가 칩이 지원하는 범위를 벗어난 경우가 많다.

## 핀 뮤잉: 하나의 핀에 여러 얼굴을 주기

현대 SoC는 수백 개의 기능(UART, I2C, SPI, GPIO, CAN 등)을 지원하지만, 칩의 물리적인 핀 개수는 그보다 훨씬 적다. 이 문제를 해결하기 위해 SoC 설계자는 하나의 물리적 핀이 여러 기능 중 하나로 동작할 수 있게 만들고, 소프트웨어가 레지스터 설정으로 "지금 이 핀은 어떤 기능으로 쓰겠다"를 선택하도록 한다. 이를 핀 뮤잉(pin muxing) 또는 핀 멀티플렉싱이라 한다.

예를 들어 어떤 핀은 보드 설계에 따라 "UART의 송신선"으로 쓰일 수도 있고, "일반 GPIO 출력"으로 쓰일 수도 있고, "I2C의 클럭선"으로 쓰일 수도 있다. 보드를 설계한 하드웨어 엔지니어는 실제로 그 핀을 회로 기판에서 어떤 용도로 연결했는지 결정하고, 소프트웨어 엔지니어는 그 결정에 맞춰 핀 뮤잉 레지스터를 정확히 설정해 줘야 한다. 둘이 일치하지 않으면, 예를 들어 하드웨어는 그 핀을 UART 송신선으로 배선해 놓았는데 소프트웨어가 그 핀을 GPIO로 설정해 버리면 UART 통신 자체가 전혀 동작하지 않는다.

```c
#define PINMUX_PIN12  (*(volatile uint32_t *)0x40040030UL)

/* 핀 12번을 UART1의 TX 기능으로 설정 (뮤잉 값 2) */
#define PINMUX_FUNC_GPIO   0
#define PINMUX_FUNC_I2C    1
#define PINMUX_FUNC_UART   2

void pinmux_uart1_tx(void) {
    PINMUX_PIN12 = PINMUX_FUNC_UART;
}
```

이런 설정이 보드마다 다르기 때문에, 보드 브링업 단계에서 작성하는 핀 뮤잉 설정표와 전원/클럭 설정 코드는 그 자체로 이후 디바이스 트리 작성의 바탕 자료가 된다. 실제로 양산 소프트웨어에서는 이런 초기 설정값들이 결국 디바이스 트리의 `pinctrl` 노드나 U-Boot의 보드별 초기화 코드 형태로 정리되어 들어간다. 즉 브링업 단계에서 손으로 직접 두드려 확인한 레지스터 값들이, 앞 레슨들에서 배운 디바이스 트리와 U-Boot 보드 지원 코드의 원재료가 되는 것이다.

## 전형적인 브링업 절차: 작은 성공을 쌓아 올리기

새 보드의 브링업은 한 번에 모든 것을 올리려 하지 않고, 아주 작은 단위의 성공을 하나씩 확인하며 앞으로 나아가는 방식으로 진행된다. 전형적인 순서는 다음과 같다.

- 전원 확인: 보드에 전원을 넣고, 오실로스코프로 모든 전원 레일이 올바른 전압과 순서로 올라오는지 측정한다. 이 단계에서 아직 CPU는 어떤 코드도 실행하지 않는다.
- JTAG 연결 확인: JTAG 디버거를 연결해 CPU가 디버그 포트에 응답하는지 확인한다. 이것만으로도 CPU 코어가 최소한의 생명 징후를 보이는지 알 수 있다.
- 클럭 확인: 디버거로 극히 짧은 코드를 CPU에 직접 주입해 PLL을 설정하고, lock 상태가 되는지 확인한다.
- 최소 코드로 핀 토글: 베어메탈 레슨에서 본 것과 똑같은 방식으로, 특정 GPIO 핀을 1과 0으로 반복해서 바꾸는 극히 단순한 코드를 돌려보고, 오실로스코프나 로직 분석기로 그 핀의 전압이 실제로 바뀌는지 확인한다. 이 단계가 성공하면 "CPU가 명령을 실제로 실행하고 있다"는 것이 처음으로 증명된다.
- 시리얼 콘솔 동작 확인: 핀 뮤잉을 UART로 설정하고 폴링 방식으로 문자를 출력하는 코드를 돌려, PC에서 시리얼 터미널로 글자가 보이는지 확인한다. 이 시점부터는 printf 디버깅이 가능해져 이후 과정이 훨씬 수월해진다.
- 부트로더 포팅: 여기까지 확인되면 비로소 앞 레슨에서 다룬 SPL과 U-Boot를 이 보드에 맞게 포팅하는 작업을 시작할 수 있다.
- 커널과 디바이스 트리 작성: U-Boot가 안정적으로 동작하면, 이 보드의 핀 뮤잉과 클럭 설정을 반영한 디바이스 트리를 작성하고 커널을 올려본다.

이 순서에서 볼 수 있듯, 브링업은 지금까지 이 로드맵에서 배운 모든 내용, 즉 레지스터 직접 제어, 폴링, 링커와 빌드, 부트로더, 디바이스 트리가 거꾸로 쌓아 올려지는 과정이다. 가장 밑바닥의 전원과 클럭이 확인되지 않으면 그 위의 어떤 소프트웨어 지식도 적용할 기회조차 생기지 않는다.

<details><summary><b>심화: JTAG과 바운더리 스캔</b></summary>

JTAG(Joint Test Action Group)은 원래 칩들이 보드에 납땜된 뒤 각 핀이 제대로 연결되었는지 검사하기 위한 표준(바운더리 스캔, boundary scan)으로 만들어졌지만, 오늘날에는 CPU 디버깅의 표준 인터페이스로 훨씬 널리 쓰인다. JTAG 디버거는 CPU 코어에 직접 접근해 레지스터 값을 읽고 쓰고, 메모리의 임의 위치에 값을 넣고, 심지어 아직 플래시에 아무 코드도 없는 상태에서도 디버거가 메모리에 직접 작은 코드를 주입해 실행시킬 수 있다. 브링업 초기 단계에서는 바로 이 "플래시에 아직 아무것도 없어도 디버거가 코드를 주입해 실행할 수 있다"는 점이 결정적인 역할을 한다. 아직 완성된 부트로더도 없는 상태에서 PLL 설정이나 핀 토글 같은 아주 짧은 검증 코드를 CPU에 밀어넣어 실행시켜 볼 수 있기 때문이다.

JTAG은 또한 CPU를 특정 명령어에서 멈추고(breakpoint), 한 줄씩 실행하고(single-step), 그 순간의 모든 레지스터 값을 들여다볼 수 있게 해준다. 보드 브링업 과정에서 "PLL이 lock되지 않는다"는 증상이 나타났을 때, JTAG으로 PLL 상태 레지스터의 정확한 비트 값을 그 순간에 읽어보면, 설정이 잘못 들어갔는지 아니면 하드웨어 자체의 문제인지를 구분하는 데 핵심적인 단서를 얻을 수 있다.

</details>

<details><summary><b>심화: 브라운아웃과 전원 감시 회로</b></summary>

전원 시퀀스가 설계대로 잘 올라온 뒤에도, 차량 환경은 전원이 매우 불안정한 곳이다. 배터리 전압은 시동을 걸 때(크랭킹, cranking) 순간적으로 크게 떨어질 수 있고, 다른 전장 부하가 갑자기 걸리면서 전압이 흔들리기도 한다. 전원 전압이 정상 동작 범위 아래로 순간적으로 떨어지는 현상을 브라운아웃(brownout)이라 부르는데, 이런 상황에서 CPU가 애매한 전압 상태로 계속 동작을 시도하면 레지스터 값이 무작위로 깨지거나 메모리 내용이 손상되는 매우 위험한 상태에 빠질 수 있다.

이를 막기 위해 보드에는 보통 전원 감시 회로(brownout detector 또는 전압 감시 IC)가 들어가며, 전압이 안전 한계 아래로 떨어지는 것을 감지하면 CPU에게 즉시 리셋 신호를 보내 깨끗하게 재시작하도록 만든다. 애매하게 살아 있는 상태보다, 차라리 완전히 리셋되어 처음부터 다시 시작하는 것이 훨씬 안전하다는 설계 철학이 여기에 담겨 있다. 브링업 단계에서는 이 전원 감시 회로의 임계 전압이 올바르게 설정되어 있는지도 함께 검증해야 하며, 이는 앞서 다룬 워치독 타이머가 소프트웨어의 멈춤을 감시하는 것과 비슷하게, 전원 감시 회로는 하드웨어 차원의 비정상 상태를 감시하는 짝이 되는 안전장치다.

</details>

**확인 문제.** 새 보드에 전원을 넣었는데 JTAG 디버거가 CPU에 전혀 연결되지 않는다. 어떤 순서로 원인을 좁혀나가야 하는지, 그리고 이 단계에서 아직 소프트웨어 디버깅을 시도하는 것이 적절하지 않은 이유를 설명하라.
<details><summary>답 보기</summary>

가장 먼저 확인해야 할 것은 전원 시퀀스다. 오실로스코프로 각 전원 레일의 전압이 데이터시트가 요구하는 순서와 타이밍대로 올라오는지 측정해야 한다. 전원 레일 중 하나라도 올라오지 않거나 순서가 잘못되었다면 CPU 코어 자체가 정상적으로 깨어나지 못하므로 JTAG 디버거가 응답을 받을 수 없다. 전원이 정상이라면, 그 다음으로 클럭 발진기가 실제로 발진하고 있는지(오실로스코프로 발진 파형 확인), JTAG 커넥터의 배선이나 보드 설계 오류가 없는지를 차례로 확인한다. 이 단계는 소프트웨어가 아직 CPU 안에서 전혀 실행되지 않는, 순수하게 하드웨어적인 전제조건이 충족되었는지를 확인하는 단계다. 전원과 클럭, JTAG 연결 자체가 보장되지 않은 상태에서는 어떤 소프트웨어 코드를 작성하고 분석해도 무의미하며, 반드시 하드웨어 레벨의 원인을 먼저 배제해야 한다.

</details>

**확인 문제.** 보드 설계자는 특정 물리 핀을 I2C의 클럭선(SCL)으로 배선했지만, 소프트웨어 엔지니어가 핀 뮤잉 레지스터에 그 핀을 GPIO 기능으로 설정했다. 이때 어떤 문제가 나타나며, 왜 이것이 소프트웨어만 봐서는 바로 알아채기 어려운 문제인지 설명하라.
<details><summary>답 보기</summary>

I2C 드라이버가 클럭 신호를 내보내려는 코드를 정상적으로 실행하더라도, 실제 핀은 GPIO 기능으로 설정되어 있어 I2C 컨트롤러의 출력 신호가 그 핀으로 전달되지 않는다. 그 결과 I2C 버스에 연결된 센서들과 통신이 전혀 이루어지지 않거나, 버스가 응답 없는 상태로 멈춰버린다. 소프트웨어 코드 자체, 즉 I2C 드라이버의 로직이나 레지스터 설정값은 겉보기에 완전히 정상이기 때문에, 코드만 읽어서는 문제를 발견하기 어렵다. 실제 원인은 소프트웨어의 핀 뮤잉 설정과 하드웨어 설계자가 그 핀을 배선한 용도가 서로 일치하지 않는다는, 소프트웨어와 하드웨어 설계 문서 사이의 불일치에 있다. 이런 문제는 로직 분석기나 오실로스코프로 해당 핀의 실제 전기적 동작을 직접 들여다보고, 보드의 회로도와 핀 뮤잉 설정표를 나란히 대조해야만 발견할 수 있다.

</details>

## 정리

- 보드 브링업은 전원, 클럭, 핀 뮤잉처럼 소프트웨어가 동작하기 위한 가장 기초적인 하드웨어 조건이 아직 검증되지 않은 새 보드에 처음 생명을 불어넣는 과정이다.
- 전원 시퀀스는 여러 전원 레일을 정해진 순서와 타이밍으로 올려야 하며, 이를 지키지 않으면 칩이 영구적으로 손상될 수 있다.
- 클럭 트리는 하나의 수정 발진기로부터 PLL을 통해 CPU, 버스, 주변장치가 필요로 하는 여러 다른 주파수를 만들어내며, PLL이 lock 상태가 되었는지 확인하는 것이 브링업의 핵심 단계다.
- 핀 뮤잉은 하나의 물리적 핀을 여러 기능 중 하나로 소프트웨어가 선택하는 메커니즘이며, 하드웨어 설계의 배선 의도와 소프트웨어 설정이 정확히 일치해야 한다.
- 브링업은 전원 확인, JTAG 연결, 클럭 확인, 핀 토글, 시리얼 콘솔 순으로 작은 성공을 하나씩 쌓아 올리는 방식으로 진행되며, 그 결과물이 이후 부트로더 포팅과 디바이스 트리 작성의 바탕이 된다.

이번 레슨에서는 가장 밑바닥의 전원과 클럭, 핀 설정부터 시작해 베어메탈 코드가 처음으로 살아 움직이기까지의 과정을 살펴보았다. 이는 이 로드맵에서 배운 레지스터 제어, 링커와 빌드, 부트로더, 디바이스 트리 지식이 실제로 새 하드웨어 위에서 맞물려 돌아가는 가장 구체적인 현장이며, 이후 어떤 ECU 소프트웨어를 다루더라도 그 바탕에는 이번 레슨에서 다룬 브링업 과정이 이미 자리하고 있다.

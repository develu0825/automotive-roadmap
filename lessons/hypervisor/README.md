# 하이퍼바이저 · 혼합중요도

앞서 `car-framework` 에서는 안드로이드 위의 CarService 와 AIDL 로 인포테인먼트 화면이 차량 데이터를 주고받는 구조를 배웠고, `autosar-adaptive` 에서는 POSIX 기반 운영체제 위에서 돌아가는 제어 영역 소프트웨어를 배웠다. 그런데 이 두 세계는 지금까지 서로 다른 칩, 서로 다른 전자제어장치(ECU, Electronic Control Unit) 위에서 따로 동작하는 것처럼 이야기해 왔다. 한쪽은 커다란 중앙 화면을 그리는 안드로이드, 다른 한쪽은 브레이크나 조향에 관여하는 AUTOSAR 제어기다. 이번 장의 질문은 단순하다. 이 둘을 하나의 칩, 즉 하나의 SoC(System on Chip) 위에 함께 올릴 수 있을까. 그리고 올린다면 무엇을 조심해야 할까.

이런 수요가 생기는 이유는 현실적이다. 최근 차량 한 대에는 수십 개에서 백 개가 넘는 ECU 가 들어간다. ECU 가 많아질수록 부품값, 배선 무게, 설치 공간, 전력 소모, 그리고 그 모두를 관리하는 복잡도가 함께 올라간다. 반대로 요즘 고성능 SoC 는 여러 개의 CPU 코어와 넉넉한 메모리, 강력한 그래픽 처리 장치를 한 칩에 담고 있어서, 사실 안드로이드 인포테인먼트 하나만 돌리기에는 성능이 남아돈다. 그렇다면 그 남는 성능 위에 AUTOSAR 제어 영역까지 함께 올려 ECU 두 개를 하나로 합치면 비용과 공간과 전력을 한꺼번에 아낄 수 있다. 이것이 자동차 업계가 "통합(consolidation)" 이라고 부르는 흐름이고, 그 핵심 기술이 바로 하이퍼바이저(hypervisor) 다.

문제는 이 둘의 성격이 완전히 다르다는 데 있다. 안드로이드 인포테인먼트는 사용자가 앱을 설치하고, 화면이 가끔 버벅이거나 앱이 죽어도 큰일이 나지 않는 영역이다. 반면 AUTOSAR 제어 로직은 늦거나 멈추면 그 자체가 사고로 이어질 수 있는 안전 영역이다. 만약 이 둘을 아무 장치 없이 그냥 한 OS 위에 나란히 올린다면, 안드로이드에서 돌던 어떤 앱이 메모리를 폭주시키거나 CPU 를 독차지하는 순간, 바로 옆에서 돌던 제어 로직이 데드라인을 놓치게 된다. 즉, 재미로 깔아 둔 앱 하나가 조향 제어를 지연시킬 수 있다는 뜻이다. 이것은 결코 허용될 수 없다. 이번 장에서는 가상화가 무엇인지부터 시작해, 하이퍼바이저가 어떻게 이 두 세계를 한 칩 위에서 서로 침범하지 못하게 갈라 놓는지를 단계적으로 살펴본다.

## 학습 목표

- 가상화와 가상 머신(VM)의 기본 개념을 설명하고, 한 SoC 에 여러 게스트 OS 를 올린다는 것이 무슨 의미인지 이해한다.
- Type-1(bare-metal) 하이퍼바이저와 Type-2 하이퍼바이저의 차이를 구분하고, 자동차에서 왜 Type-1 이 선호되는지 설명할 수 있다.
- 혼합 중요도(mixed-criticality) 시스템과 "간섭으로부터의 자유(freedom from interference)" 가 왜 핵심 요구사항인지 ISO 26262 관점에서 설명할 수 있다.
- 하이퍼바이저가 CPU · 메모리 · I/O 파티셔닝과 VM 간 통신 중재로 격리를 실제로 구현하는 메커니즘을 설명할 수 있다.
- 안전 영역 VM 에게 보장된 CPU 시간 예산을 주는 정적 시간 분할 스케줄링의 사고방식을 설명할 수 있다.

## 가상화와 가상 머신: 한 하드웨어 위의 여러 컴퓨터

가상화(virtualization)의 기본 아이디어는, 하나의 물리 하드웨어 위에서 마치 여러 대의 독립된 컴퓨터가 동시에 돌아가는 것처럼 만드는 것이다. 이때 이 "가상의 컴퓨터" 하나하나를 가상 머신(VM, Virtual Machine)이라 부른다. 각 VM 은 자신이 진짜 하드웨어를 혼자 쓰고 있다고 착각하면서, 그 위에 자신만의 운영체제를 올린다. 이렇게 VM 안에서 돌아가는 OS 를 게스트 OS(guest OS)라 한다.

자동차 통합 시나리오로 옮겨 보면 그림이 선명해진다. 하나의 SoC 위에 VM 을 두 개 만든다. 첫 번째 VM 에는 `car-framework` 에서 배운 안드로이드를 게스트 OS 로 올려 인포테인먼트 화면을 그리게 하고, 두 번째 VM 에는 `autosar-adaptive` 의 POSIX 기반 OS 를 게스트 OS 로 올려 제어 영역을 담당하게 한다. 두 VM 은 같은 칩 안에 있지만 서로를 직접 볼 수 없고, 각자 별개의 컴퓨터인 것처럼 동작한다. 사용자가 안드로이드 쪽에서 아무리 앱을 깔고 지우고 화면을 바꿔도, 제어 영역 VM 은 그 사실조차 알지 못한 채 자기 일만 묵묵히 한다. 이것이 가상화가 주는 가장 큰 가치, 즉 격리(isolation)다.

여기서 한 가지를 분명히 해 두자. 가상화는 단순히 "두 프로그램을 같이 돌리는 것" 과는 근본적으로 다르다. 한 OS 안에서 앱 두 개를 동시에 실행하면 그 둘은 같은 커널, 같은 메모리 관리자, 같은 스케줄러를 공유한다. 그래서 한쪽이 커널을 망가뜨리거나 자원을 독점하면 다른 쪽도 함께 무너진다. 반면 VM 두 개는 서로 다른 OS 를 통째로 가지므로, 한 VM 안에서 게스트 OS 커널이 통째로 죽어도 그것은 그 VM 안에서 끝나는 일이다. 바로 이 "커널 단위의 격리" 가 안전 영역과 비안전 영역을 한 칩에 섞을 때 필요한 수준의 분리다.

## 하이퍼바이저의 역할과 Type-1 구조

그렇다면 이 여러 VM 을 누가 만들고 관리하는가. 그 역할을 맡는 소프트웨어가 하이퍼바이저(hypervisor)다. 하이퍼바이저는 각 VM 에게 CPU 시간, 메모리 영역, I/O 장치를 나눠 주고, VM 들이 서로의 영역을 침범하지 못하도록 격리를 강제하는 관리자다. 쉽게 말해 하이퍼바이저는 "VM 들의 운영체제" 에 해당한다. 일반 OS 가 여러 앱을 관리하듯, 하이퍼바이저는 여러 OS(게스트 OS) 를 관리한다.

하이퍼바이저는 크게 두 종류로 나뉜다. Type-1 하이퍼바이저는 물리 하드웨어 위에 직접 올라간다. 하드웨어 바로 위에 하이퍼바이저가 있고, 그 위에 여러 VM 이 얹히는 구조다. 그래서 bare-metal 하이퍼바이저라고도 부른다. 반면 Type-2 하이퍼바이저는 이미 깔려 있는 일반 호스트 OS(예: 데스크톱의 윈도우나 리눅스) 위에 하나의 응용 프로그램처럼 설치되어, 그 안에서 또 다른 OS 를 돌린다. 개인용 컴퓨터에서 가상화 소프트웨어를 깔아 그 안에 다른 OS 를 띄워 보는 경험이 바로 Type-2 다.

자동차 제어 영역에서는 거의 예외 없이 Type-1 을 쓴다. 이유는 두 가지다. 첫째, 결정론성(determinism)이다. Type-2 는 아래에 깔린 호스트 OS 의 스케줄러와 메모리 관리의 영향을 그대로 받는다. 호스트 OS 가 어떤 이유로 바빠지면 그 위의 VM 도 함께 느려지고, 그 지연을 예측하기가 매우 어렵다. 안전 영역 제어 로직은 "최악의 경우에도 몇 ms 안에 끝난다" 는 것을 미리 보장해야 하는데, 두꺼운 호스트 OS 가 중간에 끼어 있으면 그 보장을 하기가 어렵다. Type-1 은 하드웨어 바로 위에 얇게 올라가 자원 배분을 직접 통제하므로 훨씬 예측 가능한 타이밍을 제공한다.

둘째, 신뢰 경계(trust boundary)의 크기다. 시스템에서 "반드시 믿을 수 있어야 하는 부분", 즉 그것이 틀리면 전체 안전이 무너지는 핵심 영역을 신뢰 기반(TCB, Trusted Computing Base)이라 한다. Type-2 는 그 아래에 거대하고 복잡한 범용 호스트 OS 전체가 깔려 있어서, 그 호스트 OS 의 수백만 줄짜리 코드가 통째로 신뢰 기반에 들어간다. 코드가 많다는 것은 결함이 숨어 있을 여지도 많다는 뜻이다. Type-1 하이퍼바이저는 하는 일을 자원 배분과 격리로 좁혀 코드 규모를 최대한 작게 유지한다. 작은 코드는 검증하기 쉽고, 검증하기 쉬운 코드는 안전 인증을 받기 쉽다. 그래서 작은 신뢰 경계가 자동차에서 Type-1 을 선호하는 핵심 이유다.

## 혼합 중요도 시스템과 간섭으로부터의 자유

이제 이번 장의 가장 중요한 개념으로 들어가자. 하나의 칩 안에 안전 등급이 서로 다른 소프트웨어가 함께 사는 시스템을 혼합 중요도(mixed-criticality) 시스템이라 부른다. 자동차 기능안전 표준인 ISO 26262 에서는 각 기능에 ASIL(Automotive Safety Integrity Level)이라는 안전 등급을 매긴다. 위험이 크고 엄격하게 관리해야 하는 기능일수록 높은 등급(ASIL A 에서 D 로 갈수록 엄격)을 받고, 안전과 직접 관련이 없는 기능은 QM(Quality Management)으로 분류된다. 인포테인먼트 안드로이드는 보통 QM 수준으로 다뤄지고, 제어 영역 AUTOSAR 로직은 ASIL 등급을 받는다. 통합 SoC 는 이 QM 소프트웨어와 ASIL 소프트웨어를 한 칩에 함께 올리는, 전형적인 혼합 중요도 시스템이다.

여기서 결정적인 요구사항이 등장한다. 바로 간섭으로부터의 자유(freedom from interference)다. ISO 26262 의 관점에서 보면, 안전 등급이 낮은 쪽(QM 안드로이드)에서 어떤 결함이 생기더라도 그것이 안전 등급이 높은 쪽(ASIL AUTOSAR)의 동작에 영향을 주어서는 안 된다. 만약 낮은 등급 소프트웨어가 높은 등급 소프트웨어를 망가뜨릴 수 있다면, 결국 전체 시스템을 가장 높은 등급 기준으로 전부 다시 검증해야 한다. 즉 안드로이드 인포테인먼트 코드 전부를 ASIL 수준으로 개발하고 인증해야 한다는 뜻인데, 수천만 줄 규모의 안드로이드를 그렇게 다루는 것은 현실적으로 불가능하다.

그래서 통합의 전제 조건은 이 간섭을 구조적으로 차단하는 것이다. 차단해야 할 간섭은 크게 두 종류다. 하나는 공간적 간섭으로, 한쪽이 다른 쪽의 메모리나 장치를 함부로 읽거나 덮어쓰는 경우다. 다른 하나는 시간적 간섭으로, 한쪽이 CPU 나 버스 같은 자원을 과도하게 점유해 다른 쪽이 제때 실행되지 못하게 하는 경우다. 따라서 하이퍼바이저가 보장해야 하는 것은 공간적 분리(spatial separation)와 시간적 분리(temporal separation) 두 가지다. 이 분리가 충분히 강하게 증명되면, 안드로이드 쪽은 QM 수준으로 개발하고 제어 영역만 ASIL 수준으로 개발해도, 둘 사이에 간섭이 없다는 사실 자체가 안전 논증의 근거가 된다. 바로 이 지점이 하이퍼바이저가 단순한 편의 기술이 아니라 안전 기술인 이유다.

## 하이퍼바이저가 격리를 구현하는 메커니즘

간섭으로부터의 자유는 선언만으로 얻어지지 않는다. 하이퍼바이저는 하드웨어의 도움을 받아 이를 물리적으로 강제한다. 구체적인 메커니즘을 네 가지로 나눠 보자.

첫째는 CPU 파티셔닝이다. SoC 에는 보통 여러 개의 CPU 코어가 있다. 가장 단순하고 강력한 방법은 코어를 아예 나눠 주는 것이다. 예를 들어 8 개 코어 중 6 개는 안드로이드 VM 에, 2 개는 제어 영역 VM 에 전용으로 할당한다. 그러면 안드로이드가 아무리 바빠도 자기에게 할당된 6 개 코어 안에서만 바쁠 뿐, 제어 영역의 2 개 코어는 건드리지 못한다. 코어가 넉넉하지 않을 때는 한 코어를 여러 VM 이 시간으로 나눠 쓰는 시간 분할 스케줄링을 쓰는데, 이 방식은 뒤에서 따로 다룬다.

둘째는 메모리 파티셔닝이다. 각 VM 에게는 물리 메모리의 서로 겹치지 않는 영역이 배정된다. 이를 강제하는 핵심 하드웨어가 MMU(Memory Management Unit)와 IOMMU(I/O Memory Management Unit)다. MMU 는 CPU 가 내보내는 메모리 접근 주소를 변환하고 검사하는 장치로, 하이퍼바이저는 MMU 를 설정해 각 VM 이 자신에게 허락된 물리 주소 범위 밖으로는 절대 접근하지 못하도록 막는다. 안드로이드 VM 이 실수로든 악의로든 제어 영역 VM 의 메모리 주소를 건드리려 하면, 그 접근은 하드웨어 차원에서 차단되고 결함으로 처리된다. IOMMU 는 같은 역할을 장치(device)의 메모리 접근에 대해 수행한다. 뒤에서 설명할 DMA(장치가 CPU 를 거치지 않고 직접 메모리를 읽고 쓰는 방식)를 어떤 장치가 사용할 때, IOMMU 가 없다면 그 장치가 아무 메모리나 건드릴 수 있어 격리에 구멍이 생긴다. IOMMU 는 장치의 메모리 접근도 VM 경계 안으로 가둔다.

셋째는 I/O 가상화다. 카메라, 저장장치, 네트워크 컨트롤러 같은 입출력 장치를 VM 들에게 어떻게 나눠 줄지의 문제다. 크게 두 가지 접근이 있다. 디바이스 패스스루(device passthrough)는 특정 장치를 통째로 한 VM 에게 전용으로 넘겨주는 방식이다. 예를 들어 안전에 중요한 어떤 센서 인터페이스를 제어 영역 VM 에게만 직접 연결하면, 그 장치는 다른 VM 과 공유되지 않아 간섭 위험이 가장 낮고 성능도 좋다. 반대로 화면이나 저장장치처럼 여러 VM 이 함께 써야 하는 장치는 하나의 물리 장치를 가상화해 공유한다. 이때는 하이퍼바이저(또는 그 역할을 위임받은 특정 관리용 VM)가 중간에서 요청을 중재해, 한 VM 의 입출력이 다른 VM 의 입출력을 방해하거나 데이터를 엿보지 못하도록 통제한다.

넷째는 VM 간 통신이다. 완전히 격리만 하면 두 VM 은 서로 아무것도 주고받을 수 없는데, 실제로는 제한된 통신이 필요하다. 예를 들어 제어 영역이 감지한 차량 속도나 경고 상태를 안드로이드 화면에 띄워야 한다. 이때 두 VM 을 직접 연결하는 대신, 하이퍼바이저가 중재하는 좁고 명확한 통로만 열어 둔다. 대표적인 방식이 하이퍼바이저가 관리하는 공유 메모리 채널이나, 차량 내부 통신을 흉내 낸 가상 CAN(virtual CAN) 채널이다. 핵심은 이 통로가 하이퍼바이저의 통제 아래 있는 단 하나의 정해진 경로라는 점이다. 통신 창구를 좁고 명확하게 제한할수록 그 창구만 집중적으로 검증하면 되므로, 격리를 유지하면서도 필요한 데이터만 안전하게 주고받을 수 있다.

## 하이퍼바이저 스케줄링: 보장된 시간 예산

CPU 코어를 VM 전용으로 통째로 나눠 줄 수 있으면 가장 깔끔하지만, 코어 수가 한정적이라 한 코어를 여러 VM 이 나눠 써야 하는 경우가 많다. 이때 하이퍼바이저의 스케줄링 방식이 시간적 분리의 성패를 가른다. 여기서 자동차 하이퍼바이저가 택하는 사고방식은 일반 OS 의 스케줄러와 결이 다르다.

일반 데스크톱 OS 의 스케줄러는 평균적으로 모두에게 공평하게, 그리고 전체 처리량이 최대가 되도록 CPU 를 나눠 주는 데 초점을 맞춘다. 하지만 혼합 중요도 시스템에서는 "평균적으로 공평" 한 것이 오히려 위험하다. 안드로이드가 바쁠 때 제어 영역의 몫까지 끌어다 쓰면 제어 영역이 데드라인을 놓치기 때문이다. 그래서 하이퍼바이저는 다른 접근을 쓴다. 안전 영역 VM 에게 미리 보장된 CPU 시간 예산(time budget)을 정적으로 떼어 주는 것이다.

구체적으로는 시간을 일정한 주기로 쪼개고, 그 주기 안에서 각 VM 이 CPU 를 쓸 시간 구간을 미리 정해 둔다. 예를 들어 1 ms 주기를 두고, 그중 앞의 0.3 ms 는 무조건 제어 영역 VM 에게 주고 나머지 0.7 ms 를 안드로이드 VM 이 쓰도록 고정하는 식이다. 이렇게 하면 안드로이드가 아무리 바빠도 제어 영역에게 보장된 0.3 ms 는 절대 침범하지 못한다. 반대로 제어 영역이 자기 시간을 다 쓰지 않으면 남는 시간을 안드로이드가 활용할 수 있다. 즉 안전 영역에게는 보장된 최소 예산을 확정적으로 주고, 비안전 영역은 그 위에서 남는 자원을 유연하게 쓰는 구조다.

이 발상은 사실 자동차보다 먼저 항공전자(avionics) 분야에서 정립되었다. 항공 소프트웨어 표준인 ARINC 653 은 여러 응용을 "파티션(partition)" 으로 나누고, 각 파티션에 고정된 시간 창(time window)과 메모리 영역을 배정해 서로 간섭하지 못하게 하는 파티셔닝 개념을 일찍부터 정의했다. 하이퍼바이저가 안전 영역 VM 에게 보장된 시간 창을 떼어 주는 사고방식은 이 ARINC 653 파티셔닝과 같은 뿌리에서 나온 것이다. 핵심은 "누가 얼마나 CPU 를 쓸지" 를 실행 중에 상황 봐 가며 정하는 것이 아니라, 설계 시점에 확정해 두고 그대로 강제한다는 점이다. 이 정적이고 예측 가능한 성질이야말로 안전 논증의 근거가 된다.

<details><summary><b>심화: 하드웨어 가상화 확장과 2단계 주소 변환</b></summary>

초기의 가상화는 순전히 소프트웨어 기교로 구현되었고, 그래서 느리고 복잡했다. 게스트 OS 가 하드웨어를 직접 만지려는 모든 시도를 하이퍼바이저가 일일이 가로채 흉내 내 줘야 했기 때문이다. 이 문제를 근본적으로 해결한 것이 CPU 에 들어간 하드웨어 가상화 확장(hardware virtualization extension)이다. 예를 들어 널리 쓰이는 ARM 아키텍처 계열은 CPU 에 하이퍼바이저 전용 실행 권한 단계를 따로 두어, 게스트 OS 보다 더 높은 권한에서 하이퍼바이저가 동작하도록 한다. 게스트 OS 가 민감한 동작을 하려 하면 CPU 가 자동으로 하이퍼바이저에게 제어를 넘겨주므로, 하이퍼바이저는 꼭 필요한 순간에만 개입하면 된다.

메모리 격리에서 특히 중요한 것이 2단계 주소 변환(two-stage address translation)이다. 일반 시스템에서 OS 는 가상 주소를 물리 주소로 한 번 변환한다. 가상화에서는 여기에 단계가 하나 더 붙는다. 게스트 OS 는 자신이 쓰는 가상 주소를 "게스트가 물리 주소라고 믿는 주소" 로 변환하고(1단계), 하드웨어가 그 주소를 다시 진짜 물리 주소로 변환한다(2단계). 이 2단계 변환 표는 하이퍼바이저가 관리하므로, 게스트 OS 가 아무리 자기 주소 표를 조작해도 결국 하이퍼바이저가 정해 둔 물리 메모리 범위를 벗어날 수 없다. 즉 메모리 파티셔닝이 소프트웨어의 선의가 아니라 하드웨어 구조로 강제된다. 이것이 공간적 분리를 저비용으로, 그리고 신뢰할 수 있게 구현하는 토대다.

</details>

<details><summary><b>심화: 하이퍼바이저 자체의 안전 인증</b></summary>

하이퍼바이저는 모든 VM 아래에 깔려 자원 배분과 격리를 책임지는 유일한 공통 계층이다. 바꿔 말하면, 하이퍼바이저에 결함이 있어 격리가 깨지는 순간 간섭으로부터의 자유라는 전제 전체가 무너진다. 그래서 하이퍼바이저는 앞서 말한 신뢰 기반(TCB)의 핵심이며, 그 자체가 시스템에서 가장 높은 안전 등급으로 검증되어야 한다. 안드로이드 VM 을 QM 으로 두고 제어 VM 을 ASIL 로 두는 분리 전략이 성립하려면, 그 분리를 강제하는 하이퍼바이저는 적어도 제어 VM 과 같은 수준, 보통은 가장 엄격한 등급의 검증을 받아야 한다.

이것이 바로 Type-1 하이퍼바이저를 얇고 작게 유지하려는 설계 철학과 직결된다. 검증해야 할 코드가 적을수록 결함 가능성이 줄고, 모든 실행 경로를 분석해 "어떤 경우에도 격리가 깨지지 않는다" 는 것을 논증하기가 쉬워진다. 그래서 자동차용 하이퍼바이저는 범용 기능을 욕심내지 않고, 자원 분배 · 메모리 보호 · 스케줄링 · 중재된 통신이라는 꼭 필요한 역할만 담으려 한다. 상용으로는 예를 들어 자동차 기능안전 인증을 받은 상용 하이퍼바이저들이 이 영역에서 쓰이며, 이들은 작은 코드 규모와 결정론적 동작, 그리고 인증 근거 자료를 함께 제공하는 것을 핵심 가치로 내세운다.

</details>

**확인 문제.** 어떤 엔지니어가 비용을 아끼려고, 안드로이드 인포테인먼트와 ASIL 등급 제어 로직을 하이퍼바이저 없이 하나의 OS 위에 일반 응용 프로그램 두 개로 나란히 올리자고 제안했다. 이 방식이 ISO 26262 의 간섭으로부터의 자유 관점에서 왜 받아들여지기 어려운지 설명하라.

<details><summary>답 보기</summary>

하나의 OS 위에 두 프로그램을 올리면 둘은 같은 커널, 같은 메모리 관리자, 같은 스케줄러를 공유하게 된다. 그러면 QM 수준인 안드로이드 쪽의 결함이 ASIL 쪽에 영향을 줄 경로가 열려 있다. 공간적으로는 안드로이드 쪽 코드의 오류가 공유 커널이나 제어 영역의 메모리를 망가뜨릴 수 있고, 시간적으로는 안드로이드 쪽이 CPU 를 과도하게 점유해 제어 로직이 데드라인을 놓치게 만들 수 있다. 즉 공간적 · 시간적 간섭이 모두 가능하다.

ISO 26262 의 간섭으로부터의 자유 원칙에 따르면, 낮은 등급 소프트웨어의 결함이 높은 등급 소프트웨어에 영향을 주지 못한다는 것을 보장할 수 없다면, 결국 두 소프트웨어 전체를 가장 높은 등급(ASIL)으로 개발하고 검증해야 한다. 수천만 줄 규모의 안드로이드를 ASIL 수준으로 인증하는 것은 현실적으로 불가능하므로, 이 제안은 받아들여지기 어렵다. 하이퍼바이저로 두 영역을 각각 별개의 VM 에 넣어 공간적 · 시간적으로 분리하고, 그 분리를 하드웨어로 강제해야만 안드로이드는 QM 으로, 제어 로직만 ASIL 로 개발하는 분리 전략이 성립한다.

</details>

**확인 문제.** 하이퍼바이저가 안전 영역 VM 에게 "1 ms 주기마다 보장된 0.3 ms" 를 정적으로 떼어 주는 시간 분할 방식을 쓴다고 하자. 이 방식이 일반 데스크톱 OS 의 "공평하게 나눠 주는" 스케줄링보다 자동차 제어 영역에 적합한 이유를 설명하라.

<details><summary>답 보기</summary>

데스크톱 OS 의 스케줄러는 전체 처리량과 평균적인 공평성을 목표로 하므로, 어떤 VM 이 실제로 언제 얼마만큼 CPU 를 받을지가 그때그때의 부하 상황에 따라 달라진다. 제어 영역은 "최악의 경우에도 정해진 시간 안에 반드시 끝난다" 는 것을 미리 보장해야 하는데, 이렇게 상황에 따라 변하는 스케줄링에서는 그 최악의 경우를 예측하고 보장하기가 어렵다.

반면 보장된 시간 예산을 정적으로 떼어 주는 방식은, 안드로이드가 아무리 바빠도 제어 영역에게 약속된 0.3 ms 를 절대 침범하지 못하도록 설계 시점에 확정한다. 덕분에 제어 영역은 매 주기마다 최소한의 실행 시간을 확정적으로 확보하고, 이를 근거로 데드라인 준수를 수학적으로 논증할 수 있다. 즉 시간적 분리가 예측 가능하고 확정적이라는 점이 핵심이며, 남는 시간은 비안전 영역이 유연하게 쓰면 되므로 자원 낭비도 크지 않다.

</details>

## 정리

- 통합(consolidation) 수요는 비용 · 공간 · 전력 절감에서 나온다. 성능이 남는 하나의 SoC 위에 인포테인먼트 안드로이드와 제어 영역 AUTOSAR 를 함께 올려 ECU 를 줄이려는 것이다. 그 핵심 기술이 하이퍼바이저다.
- 가상화는 하나의 물리 하드웨어 위에 여러 독립된 VM 을 만들고, 각 VM 이 자신만의 게스트 OS 를 올리게 한다. 커널 단위로 격리되므로 한쪽의 결함이 다른 쪽을 무너뜨리지 않는다.
- 하이퍼바이저는 VM 들에게 자원을 배분하고 격리를 강제하는 관리자다. 자동차에서는 결정론성과 작은 신뢰 경계 때문에 하드웨어 바로 위에 얇게 올라가는 Type-1(bare-metal) 하이퍼바이저가 선호된다.
- 혼합 중요도 시스템에서는 ISO 26262 의 간섭으로부터의 자유가 핵심 요구사항이다. 낮은 등급(QM 안드로이드)의 결함이 높은 등급(ASIL 제어)에 공간적 · 시간적으로 간섭하지 못하도록 분리해야, 각 영역을 제 등급으로만 개발할 수 있다.
- 하이퍼바이저는 CPU 파티셔닝, MMU · IOMMU 를 이용한 메모리 파티셔닝, 패스스루와 공유로 나뉘는 I/O 가상화, 그리고 하이퍼바이저가 중재하는 좁은 VM 간 통신 통로로 격리를 실제로 구현한다.
- 안전 영역 VM 에게 보장된 CPU 시간 예산을 정적으로 떼어 주는 시간 분할 스케줄링은 ARINC 653 파티셔닝과 같은 뿌리를 가지며, 설계 시점에 확정된 예측 가능한 분리를 제공한다.

이번 장에서 배운 하이퍼바이저 기반 격리는 `car-framework` 의 안드로이드 인포테인먼트와 `autosar-adaptive` 의 제어 영역이라는, 성격이 정반대인 두 세계를 하나의 칩 위에서 안전하게 공존시키는 다리다. 다음 단계로 나아가면, 이렇게 한 SoC 안에서 분리된 VM 들이 다시 차량 전체의 네트워크 및 안전 아키텍처 속에서 어떻게 통합되고 검증되는지를 다루게 된다.

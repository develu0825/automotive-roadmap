# UDS 진단

정비소에서 자동차를 점검할 때 정비사가 진단기를 커넥터에 꽂으면 화면에 "엔진 냉각수 온도 센서 회로 오류" 같은 메시지가 뜨는 것을 본 적이 있을 것이다. 이 짧은 메시지 하나가 나오기까지는 꽤 복잡한 과정이 숨어 있다. 진단기는 어떤 형식으로 ECU에 질문을 던져야 하는지, ECU는 자신이 감지한 수백 가지 이상 징후 중 어떤 것을 어떤 형식으로 돌려줘야 하는지, 그리고 그 오류가 "지금 당장 발생 중인지" 아니면 "과거에 한 번 있었지만 지금은 괜찮은지"까지 구분해 전달해야 한다. 이 모든 질문과 응답의 형식이 제조사마다 다르다면, 정비소는 차종마다 완전히 다른 진단기를 써야 하고, 부품 회사는 ECU마다 다른 진단 로직을 새로 만들어야 한다.

앞서 CAN · LIN 통신에서 ECU들이 평소에 주고받는 메시지(차속, RPM, 온도 같은 신호)를 배웠다면, 이번 레슨에서는 조금 다른 성격의 통신을 다룬다. 평소 신호는 "지금 상태가 어떤지"를 계속 흘려보내는 데 반해, 진단 통신은 "외부 도구가 특정 ECU에게 콕 집어 질문하고 답을 받는" 요청/응답 방식이다. 이런 진단 통신을 모든 제조사와 ECU가 공통된 형식으로 주고받을 수 있도록 국제 표준화한 것이 UDS(Unified Diagnostic Services, 통합 진단 서비스), 정식 명칭으로는 ISO 14229다.

UDS는 단순히 오류를 보여주는 것 이상의 역할을 한다. ECU 소프트웨어를 재프로그래밍하거나, 특정 출력을 강제로 켜고 꺼서 부품이 정상 동작하는지 확인하거나, 메모리 값을 직접 읽고 쓰는 것까지 UDS의 표준 서비스 범위에 포함된다. 이번 레슨에서는 UDS의 요청/응답 메시지 구조, 자주 쓰이는 핵심 서비스들, 그리고 오류를 식별하고 저장하는 DTC(Diagnostic Trouble Code, 진단 고장 코드) 메커니즘을 차례로 살펴본다.

## 학습 목표

- UDS가 왜 필요한지, 진단 통신이 일반 CAN 신호와 어떻게 다른지 설명할 수 있다.
- UDS 요청/응답 메시지의 기본 구조(서비스 ID, 서브 펑션, 긍정·부정 응답)를 이해한다.
- 세션 제어(0x10)와 보안 접근(0x27) 서비스가 왜 함께 쓰이는지 설명할 수 있다.
- DID 기반 데이터 읽기·쓰기(0x22, 0x2E)와 루틴 제어(0x31) 서비스의 동작 방식을 이해한다.
- DTC의 상태 바이트가 어떻게 "현재 발생 중"과 "과거 발생" 상태를 구분하는지 설명할 수 있다.
- UDS가 소프트웨어 재프로그래밍(플래시)과 진단을 연결하는 지점을 개관할 수 있다.

## 왜 표준화된 진단 통신이 필요한가

ECU 하나에는 수십에서 수백 개의 센서·액추에이터 상태를 감시하는 내부 로직이 들어 있다. 이 감시 로직이 이상을 발견했을 때, 그 정보를 외부(정비소의 진단기, 또는 다른 ECU)에 어떤 형식으로 알릴지는 설계자가 자유롭게 정할 수도 있었다. 그런데 자동차 한 대에는 보통 수십 개의 ECU가 있고, 이 ECU들은 서로 다른 부품 회사가 만드는 경우가 흔하다. 각 ECU가 저마다 다른 진단 메시지 형식을 쓴다면, 정비소는 ECU마다 다른 진단 장비를 갖춰야 하고, 신차를 출시할 때마다 진단 인프라를 다시 만들어야 한다.

UDS는 이 문제를 "모든 ECU가 같은 요청 형식으로 질문받고, 같은 응답 형식으로 답한다"는 공통 규약으로 해결한다. 중요한 점은 UDS가 데이터의 의미(예: 0x1234번지에 저장된 값이 정확히 무엇을 뜻하는지)까지 통일하는 것은 아니라는 것이다. 그 의미는 제조사와 ECU마다 다를 수 있다. UDS가 통일하는 것은 "질문을 던지는 방법과 답을 받는 틀"이다. 이는 CAN · LIN 통신에서 DBC가 메시지의 신호 해석 규칙을 정의했던 것과 비슷한 역할을, 진단이라는 특수한 통신 영역에서 수행하는 셈이다.

## UDS 메시지의 기본 틀: 서비스 ID와 응답

UDS 요청은 가장 앞에 서비스 ID(Service ID, SID)라는 한 바이트를 둔다. 이 값이 "지금 무엇을 하고 싶은지"를 나타낸다. 예를 들어 0x22는 "데이터를 읽어 달라"는 요청이고, 0x2E는 "데이터를 써 달라"는 요청이며, 0x10은 "진단 세션을 바꿔 달라"는 요청이다. 많은 서비스는 서비스 ID 뒤에 서브 펑션(sub-function)이라는 바이트를 추가로 둬서 같은 서비스 안에서도 더 세부적인 동작을 구분한다. 예를 들어 세션 제어 서비스(0x10)는 서브 펑션 0x01이면 "기본 세션으로", 0x03이면 "확장 진단 세션으로" 바꾸라는 뜻이 된다.

ECU가 요청을 정상적으로 처리했다면, 요청한 서비스 ID에 0x40을 더한 값으로 응답한다. 예를 들어 0x22로 요청했다면 긍정 응답(positive response)은 0x62로 시작한다. 요청을 처리할 수 없다면 ECU는 0x7F로 시작하는 부정 응답(negative response, NRC)을 돌려주는데, 이 응답에는 원래 요청했던 서비스 ID와 함께, 왜 실패했는지를 나타내는 NRC(Negative Response Code) 값이 담긴다. 예를 들어 NRC 0x33은 "보안 접근이 거부되었다(securityAccessDenied)"는 뜻이고, 0x31은 "요청한 값이 범위를 벗어났다(requestOutOfRange)"는 뜻이다.

```
요청:  22 F1 90          (서비스 0x22, DID 0xF190 읽기 요청)
긍정 응답: 62 F1 90 57 4D 49 ... (0xF190에 저장된 데이터, 예: VIN 일부)
부정 응답: 7F 22 31          (서비스 0x22 요청이 NRC 0x31로 거부됨)
```

**확인 문제.** 진단기가 ECU에 "22 F1 86" 요청을 보냈는데, ECU로부터 "7F 22 33" 응답을 받았다. 이 응답이 의미하는 바를 설명하라.

0x7F는 부정 응답을 나타내는 머리글이고, 그다음 바이트 0x22는 원래 요청했던 서비스 ID(데이터 읽기, ReadDataByIdentifier)를 가리킨다. 마지막 바이트 0x33은 NRC 값으로, securityAccessDenied(보안 접근 거부)를 의미한다. 즉 진단기가 DID 0xF186의 값을 읽으려 했지만, ECU는 그 DID를 읽기 위해 필요한 보안 접근(0x27 서비스를 통한 잠금 해제)이 먼저 이루어지지 않았기 때문에 요청을 거부했다는 뜻이다.

## 세션 제어와 보안 접근: 아무나 할 수 없는 일을 막는 장치

UDS가 제공하는 서비스 중에는 단순히 읽는 것뿐 아니라, ECU의 동작에 직접 영향을 주는 것들도 있다. 소프트웨어를 재프로그래밍하거나, 액추에이터를 강제로 작동시키거나, 민감한 내부 값을 바꾸는 서비스가 평소에도 아무 진단기나 아무 때나 실행할 수 있다면 심각한 안전 문제로 이어질 수 있다. UDS는 이를 막기 위해 두 가지 장치를 둔다.

첫 번째는 세션 제어(Diagnostic Session Control, 서비스 ID 0x10)다. ECU는 평소 기본 세션(default session)에 머물러 있는데, 이 상태에서는 상태 조회처럼 안전한 서비스만 허용된다. 정비 작업이 필요할 때 진단기는 0x10 서비스로 확장 진단 세션(extended diagnostic session)이나 프로그래밍 세션(programming session)으로 전환을 요청하고, ECU가 이를 받아들이면 그 세션에서만 허용되는 추가 서비스들이 열린다. 세션은 또한 타임아웃을 가지고 있어서, 진단기가 일정 시간 동안 아무 요청도 보내지 않으면 ECU는 자동으로 기본 세션으로 되돌아간다. 이는 정비 작업이 끝난 뒤 민감한 세션이 계속 열려 있는 상태로 방치되는 것을 막기 위한 안전장치다.

두 번째는 보안 접근(Security Access, 서비스 ID 0x27)이다. 이는 일종의 도전-응답(challenge-response) 인증 절차로 동작한다. 진단기가 "시드(seed)를 요청한다"는 서브 펑션으로 0x27 서비스를 호출하면, ECU는 매번 다른 무작위 값인 시드를 돌려준다. 진단기(혹은 그 뒤에 있는 보안 서버)는 미리 공유된 알고리즘과 키를 이용해 이 시드로부터 키(key) 값을 계산하고, 그 계산된 키를 담아 다시 0x27 서비스를 호출한다. ECU도 같은 알고리즘으로 자신이 보낸 시드로부터 키를 계산해, 진단기가 보낸 키와 일치하는지 확인한다. 일치하면 보안 접근이 승인되어 민감한 서비스들이 열리고, 일치하지 않으면 거부된다. 매번 다른 시드를 쓰는 이유는, 과거에 주고받은 통신을 그대로 다시 재생(replay)해서 인증을 통과하려는 공격을 막기 위해서다.

<details><summary><b>심화: 왜 시드-키 알고리즘 자체는 표준에 정의되지 않는가</b></summary>

UDS 표준(ISO 14229)은 시드-키 교환의 "절차"는 정의하지만, 시드로부터 키를 계산하는 구체적인 알고리즘은 표준에 명시하지 않는다. 이는 의도된 설계다. 만약 모든 차량이 똑같은 알고리즘을 쓴다면, 그 알고리즘이 한 번 알려지는 순간 전 세계 모든 차량의 보안 접근이 동시에 뚫리는 결과가 된다.

대신 각 제조사(또는 ECU 공급사)는 자신만의 알고리즘과 키를 비공개로 설계하고, 그 알고리즘을 아는 공인된 진단 도구나 서버에만 키 계산 권한을 부여한다. 정비소의 일반 진단기는 보통 그 알고리즘을 직접 가지고 있지 않고, 제조사의 보안 서버에 시드를 전달해 키를 계산받아 온 뒤 다시 ECU에 전달하는 중계 역할만 하는 경우가 많다. 이런 구조 덕분에, 특정 제조사의 알고리즘이 유출되더라도 다른 제조사의 차량에는 영향이 미치지 않는다. 표준이 "절차"만 통일하고 "비밀"은 각자 지키게 한 것이 바로 이런 이유에서다.

</details>

## DID로 데이터 읽고 쓰기, 루틴 제어로 동작 실행하기

UDS에서 개별 데이터 항목은 DID(Data Identifier, 데이터 식별자)라는 두 바이트 번호로 식별된다. 예를 들어 VIN(차대번호)이 저장된 DID, 소프트웨어 버전이 저장된 DID, 특정 센서의 현재 측정값이 저장된 DID처럼, ECU 안의 다양한 값들이 각자의 DID 번호에 묶여 있다. 읽기 서비스(ReadDataByIdentifier, 0x22)는 DID 번호를 지정해 그 값을 조회하고, 쓰기 서비스(WriteDataByIdentifier, 0x2E)는 DID 번호와 새 값을 함께 보내 그 값을 변경한다. 어떤 DID는 읽기만 허용되고, 어떤 DID는 쓰기도 허용되며, 민감한 DID는 앞서 설명한 보안 접근이 선행되어야만 쓰기가 가능하도록 설계된다.

루틴 제어(RoutineControl, 서비스 ID 0x31)는 단순한 값 읽기·쓰기를 넘어, ECU 안에 미리 만들어진 특정 동작(루틴)을 실행시키는 서비스다. 루틴도 DID와 비슷하게 번호(Routine Identifier, RID)로 식별되며, 서브 펑션으로 "루틴 시작", "루틴 중지", "루틴 결과 요청"을 구분한다. 예를 들어 특정 액추에이터를 강제로 몇 초간 작동시켜 정상 동작 여부를 확인하는 루틴, 혹은 소프트웨어 플래시 이후 메모리 무결성을 검사하는 루틴 같은 것들이 이 서비스로 실행된다. DID가 "상태를 보거나 바꾼다"면, 루틴 제어는 "어떤 절차를 실행시킨다"는 점에서 역할이 구분된다.

## DTC: 고장을 식별하고 기억하는 방식

ECU는 이상을 감지하면 그 내용을 DTC(Diagnostic Trouble Code, 진단 고장 코드)라는 고유한 코드로 저장한다. DTC는 보통 세 바이트로 구성되는데, 앞의 두 바이트 정도가 고장의 종류를 나타내는 코드이고(흔히 P0101처럼 한 글자와 네 숫자로 표시되는 코드 체계로도 알려져 있다), 나머지 한 바이트는 상태 바이트(status byte)다.

상태 바이트는 이 고장이 "지금 이 순간에도 발생하고 있는지"와 "과거에 한 번이라도 발생한 적이 있는지"를 비트 단위로 구분해서 담는다. 예를 들어 testFailed 비트는 가장 최근 진단 테스트에서 이 고장이 실제로 감지되었는지를 나타내고, confirmedDTC 비트는 이 고장이 정해진 조건(예: 여러 주행 사이클에 걸쳐 반복 감지)을 만족해 "확정된 고장"으로 인정되었는지를 나타낸다. 이 구분이 중요한 이유는, 센서 값이 순간적으로 흔들려서 일시적으로 이상 수치가 나온 것과, 실제로 부품이 고장 난 것을 구분해야 하기 때문이다. 만약 한 번이라도 이상 신호가 잡히면 곧바로 "고장"으로 확정해 버린다면, 일시적인 잡음에도 경고등이 켜지는 과민 반응이 될 수 있다. ECU는 보통 같은 이상이 여러 주행 사이클에 걸쳐 일관되게 나타나야 confirmedDTC로 확정하고, 그래야 비로소 경고등을 켜거나 정비가 필요하다고 알린다.

DTC를 읽고 지우는 서비스도 별도로 정의되어 있다. ReadDTCInformation(0x19) 서비스는 저장된 DTC 목록을 다양한 조건(현재 활성 상태인 것만, 확정된 것만 등)으로 조회할 수 있게 하고, ClearDiagnosticInformation(0x14) 서비스는 저장된 DTC를 지운다. 정비소에서 부품을 교체한 뒤 DTC를 지우는 작업이 바로 이 0x14 서비스를 호출하는 과정이다.

**확인 문제.** 어떤 ECU가 특정 센서 회로에서 이상 신호를 딱 한 번 감지했다. 이 ECU의 DTC 상태 바이트에서 testFailed 비트는 설정되었지만 confirmedDTC 비트는 아직 설정되지 않았다. 이 상태가 의미하는 바와, 계기판 경고등이 바로 켜지지 않는 이유를 설명하라.

testFailed 비트가 설정되었다는 것은 가장 최근 진단 테스트에서 실제로 이상이 감지되었다는 뜻이지만, confirmedDTC 비트가 설정되지 않았다는 것은 아직 이 고장이 "확정된 고장"으로 인정될 만큼의 조건(예: 여러 주행 사이클에 걸친 반복 감지)을 만족하지 못했다는 뜻이다. 이는 일시적인 잡음이나 순간적인 신호 흔들림일 가능성을 배제하지 못한 상태이므로, ECU는 아직 이를 확정된 고장으로 보지 않고 경고등도 켜지 않는다. 같은 이상이 이후 주행에서도 반복되어 confirmedDTC 비트까지 설정되어야 비로소 정비가 필요한 고장으로 운전자에게 알린다.

## UDS와 소프트웨어 재프로그래밍: 진단에서 OTA로 이어지는 연결점

UDS가 지원하는 서비스 중에는 ECU의 펌웨어 자체를 새로 쓰는 작업과 직접 연결된 것들도 있다. RequestDownload(0x34), TransferData(0x36), RequestTransferExit(0x37) 같은 서비스들이 바로 그 역할을 한다. 진단기(혹은 OTA 서버와 통신하는 게이트웨이)는 먼저 세션을 프로그래밍 세션으로 전환하고 보안 접근을 통과한 뒤, 0x34로 "이만한 크기의 데이터를 이 메모리 영역에 쓰겠다"고 ECU에 알리고, 0x36으로 실제 데이터를 여러 조각으로 나눠 반복 전송하고, 마지막으로 0x37로 전송이 끝났음을 알린다. ECU는 전송받은 데이터를 자신의 플래시 메모리에 기록하고, 체크섬이나 디지털 서명으로 무결성을 검증한다.

이 흐름을 보면, UDS는 단순히 고장을 읽어내는 도구가 아니라, 차량 소프트웨어를 안전하게 갱신하는 절차의 기반이기도 하다는 것을 알 수 있다. 세션 제어로 "지금은 평소와 다른 특별한 작업을 하는 중"이라는 것을 명확히 구분하고, 보안 접근으로 권한 없는 쪽의 접근을 막은 뒤에야 실제 데이터 전송이 이루어지는 구조는, 이후 다루게 될 OTA(Over-The-Air) 업데이트에서도 그대로 이어지는 기본 원칙이다.

## 정리

- UDS(ISO 14229)는 제조사와 ECU마다 다를 수 있는 진단 통신을 "요청과 응답의 공통 형식"으로 표준화한다.
- UDS 메시지는 서비스 ID와 서브 펑션으로 요청을 구분하고, 긍정 응답(SID + 0x40)과 부정 응답(0x7F + SID + NRC)으로 결과를 돌려준다.
- 세션 제어(0x10)는 어떤 작업이 허용되는 상태인지를 구분하고, 보안 접근(0x27)은 시드-키 인증으로 민감한 서비스에 대한 권한 없는 접근을 막는다.
- DID 기반 읽기·쓰기(0x22, 0x2E)는 개별 데이터 항목을 다루고, 루틴 제어(0x31)는 ECU 안에 정의된 절차를 실행시킨다.
- DTC의 상태 바이트는 testFailed와 confirmedDTC 같은 비트로 "지금 발생 중"과 "확정된 고장"을 구분해, 일시적 잡음과 실제 고장을 가려낸다.
- RequestDownload·TransferData·RequestTransferExit 같은 서비스는 UDS를 소프트웨어 재프로그래밍, 나아가 OTA 업데이트와 연결하는 다리 역할을 한다.

UDS는 "모든 ECU가 같은 언어로 질문받고 답한다"는 약속이 왜 중요한지를 가장 분명하게 보여주는 표준이다. 이 약속이 있기 때문에 정비소는 차종과 부품 회사가 달라도 하나의 진단기로 문제를 찾아낼 수 있고, 제조사는 OTA라는 새로운 방식으로도 ECU 소프트웨어를 안전하게 갱신할 수 있는 토대를 갖게 된다. 통신과 진단이 결국 같은 질문, "이 복잡한 차량 시스템 안에서 신뢰할 수 있는 방식으로 정보를 주고받는 방법은 무엇인가"로 이어진다는 것을 기억하면, 이후 OTA 영역을 배울 때도 지금 배운 세션·보안·전송의 구조가 그대로 다시 나타나는 것을 알아볼 수 있을 것이다.

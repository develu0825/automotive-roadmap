# MISRA C · 코딩 표준

어떤 엔진 제어 소프트웨어에 다음과 같은 코드가 있다고 하자.

```c
int16_t compute_offset(int16_t base) {
    int16_t result = base * 200;
    return result;
}
```

`base`가 200보다 큰 값이면 `base * 200`은 16비트 정수(int16_t)가 표현할 수 있는 범위(약 -32768 ~ 32767)를 넘어선다. C 언어 표준은 이런 부호 있는 정수 오버플로우(signed integer overflow)를 "정의되지 않은 동작(Undefined Behavior, UB)"으로 규정한다. 정의되지 않은 동작이라는 말은 단순히 "값이 이상하게 나온다"는 뜻이 아니다. 컴파일러가 이 코드를 보고 어떤 결과를 내도 표준을 위반하지 않는다는 뜻이며, 실제로는 컴파일러 최적화 수준이나 버전에 따라 완전히 다른 기계어가 생성될 수 있다. 어제까지 "그럭저럭 동작하던" 코드가 컴파일러를 업그레이드하거나 최적화 옵션을 바꾸는 순간 전혀 다르게 동작할 수 있다는 뜻이다. 이 코드가 스로틀(throttle) 위치 계산이나 제동 압력 계산에 쓰인다면, 그 결과는 단순한 버그가 아니라 사고로 이어질 수 있는 결함이 된다.

C 언어는 1970년대에 운영체제를 구현하기 위해 설계된 언어로, 프로그래머에게 강력한 자유를 준다. 포인터 연산, 암묵적 형 변환, 정의되지 않은 동작에 대한 느슨한 규정 등은 범용 프로그래밍에서는 유용할 수 있지만, 사람의 생명과 직결된 차량 제어 소프트웨어에서는 오히려 위험 요소가 된다. 실제로 급가속 소송으로 유명해진 어느 전자식 스로틀 제어 소프트웨어 사례에서, 외부 전문가의 코드 리뷰 결과 수많은 MISRA C 가이드라인 위반과 재귀 호출, 스택 사용량이 한계에 가까운 설계가 발견되어 논란이 된 적이 있다. 이처럼 "컴파일은 되고 평소에는 동작하는" 코드와 "안전하게 동작이 보장되는" 코드 사이에는 큰 간극이 있으며, 이 간극을 좁히기 위한 산업계의 답이 MISRA C다.

MISRA(Motor Industry Software Reliability Association)는 영국 자동차 산업 컨소시엄에서 만든 코딩 표준으로, C 언어가 허용하는 전체 기능 중에서 "안전이 중요한 임베디드 시스템에서 위험하거나 모호한" 부분을 걷어내고 남은 안전한 부분집합(subset)만 사용하도록 규정한다. 앞서 배운 C++(cpp)에서 언어 자체의 문법과 의미를 익혔다면, MISRA C는 "그 언어 중에서 무엇을 쓰지 말아야 하는가"를 규정하는 규율이라고 볼 수 있다. 중요한 점은 MISRA C가 새로운 언어를 만든 것이 아니라, 표준 C 언어의 기능을 "쓰기 좋음"과 "안전함"을 기준으로 다시 선별한 것이라는 점이다. 이 레슨에서는 MISRA C가 어떤 문제를 겨냥하는지, 규칙이 어떻게 구성되어 있는지, 그리고 이를 실제로 검증하는 정적 분석 도구가 어떻게 동작하는지를 살펴본다.

## 학습 목표

- MISRA C가 해결하려는 문제(정의되지 않은 동작, 구현 정의 동작, 이식성 문제)를 설명할 수 있다.
- 지침(Directive)과 규칙(Rule), 그리고 Mandatory·Required·Advisory 분류의 차이를 구별할 수 있다.
- 대표적인 MISRA C 규칙을 코드 예시와 함께 설명할 수 있다.
- 정적 분석 도구가 MISRA C 준수를 검사하는 원리와 일탈(deviation) 관리 절차를 이해한다.
- MISRA C가 ISO 26262, ISO/SAE 21434 같은 상위 표준과 어떤 관계를 갖는지 설명할 수 있다.

## C 언어의 숨겨진 위험: 정의되지 않은 동작

C 표준은 코드의 동작을 세 가지로 구분한다.

- 정의되지 않은 동작(Undefined Behavior): 표준이 결과를 전혀 규정하지 않는 동작. 앞서 본 부호 있는 정수 오버플로우, 초기화되지 않은 변수 읽기, 배열 범위를 벗어난 접근 등이 해당한다.
- 구현 정의 동작(Implementation-Defined Behavior): 결과가 정해져 있지만 그 값은 컴파일러마다 다를 수 있는 동작. 예를 들어 `char`가 부호 있는 타입인지 없는 타입인지는 컴파일러가 정한다.
- 불특정 동작(Unspecified Behavior): 표준이 여러 가능한 결과 중 하나를 허용하지만 어느 것인지 명시하지 않는 동작. 예를 들어 함수 인자의 평가 순서가 그렇다.

이 중 가장 위험한 것은 정의되지 않은 동작이다. 구현 정의 동작은 적어도 "그 컴파일러에서는 항상 같은 결과"가 나오지만, 정의되지 않은 동작은 최적화 수준, 컴파일러 버전, 심지어 주변 코드의 변화에 따라 결과가 바뀔 수 있다. 다음 예시를 보자.

```c
int get_next(int i) {
    return i++ + i++;
}
```

이 코드는 한 표현식 안에서 같은 변수 `i`를 두 번 수정하면서 그 사이의 순서를 표준이 보장하지 않는 전형적인 정의되지 않은 동작이다. 컴파일러는 이 코드를 보고 원하는 어떤 값이든 반환하도록 코드를 생성해도 표준 위반이 아니다. 문제는 이런 코드가 리뷰 과정에서 "그냥 되는 것처럼 보인다"는 이유로 통과되기 쉽다는 점이다. MISRA C는 바로 이런 "눈으로는 멀쩡해 보이지만 표준상 결과가 보장되지 않는" 패턴들을 금지 목록으로 만들어, 사람이 매번 표준 문서를 뒤지지 않고도 위험한 코드를 걸러낼 수 있게 한다.

## 지침과 규칙, 그리고 준수 등급

MISRA C의 요구사항은 두 가지 종류로 나뉜다.

- 지침(Directive): 코드 자체만 보고는 기계적으로 판단할 수 없고, 설계 의도나 프로젝트 맥락을 함께 고려해야 하는 요구사항. 예를 들어 "컴파일러 경고를 모두 확인하고 정당화되지 않은 경고가 없어야 한다"는 식이다.
- 규칙(Rule): 코드 자체만 보고 기계적으로 판단할 수 있는, 더 구체적인 요구사항. 예를 들어 "goto 문을 사용하지 말라"처럼 코드 패턴으로 검출 가능하다.

규칙은 다시 decidable(코드만 보면 위반 여부를 항상 확정할 수 있는 규칙)과 undecidable(이론적으로 모든 경우를 확정할 수 없어 정적 분석이 "확실한 위반"과 "위반 가능성"을 구분해야 하는 규칙)로 나뉜다. 예를 들어 "재귀 함수를 사용하지 말라"는 코드 구조만 보면 검출할 수 있어 decidable에 가깝지만, "모든 실행 경로에서 변수가 항상 초기화된 뒤 사용되는가"는 모든 실행 경로를 추적해야 하므로 undecidable에 가깝다.

또한 모든 요구사항은 준수 강도에 따라 세 등급으로 분류된다.

- Mandatory(필수): 어떤 이유로도 위반이 허용되지 않는다. 일탈(deviation) 자체가 금지된다.
- Required(요구): 반드시 지켜야 하지만, 정당한 기술적 근거와 문서화를 거치면 예외(deviation)가 허용될 수 있다.
- Advisory(권고): 지키는 것이 좋지만, 상황에 따라 유연하게 적용할 수 있다.

이 세 등급의 존재는 MISRA C가 "모든 규칙을 무조건 지켜야 하는 경직된 체크리스트"가 아니라, "어디까지는 절대 양보할 수 없고, 어디서부터는 근거를 남기고 조정할 수 있는가"를 구분하는 실용적인 체계임을 보여준다.

## 대표적인 규칙으로 보는 MISRA C의 사고방식

몇 가지 대표 규칙을 통해 MISRA C가 어떤 식으로 위험을 줄이는지 살펴보자.

필수 타입 모델(essential type model)과 관련된 규칙은 암묵적 형 변환으로 값이 손실되는 상황을 막는다.

```c
uint8_t sensor_raw = 250U;
int8_t  signed_value = sensor_raw;
```

`uint8_t`(부호 없는 8비트, 0 ~ 255)인 값을 `int8_t`(부호 있는 8비트, -128 ~ 127)에 대입하면 250이라는 값은 표현 범위를 벗어나 구현 정의 동작으로 처리된다. MISRA C는 이런 "타입이 다른데 암묵적으로 변환되는" 대입을 금지하거나 명시적인 캐스트(cast)와 범위 검사를 요구한다.

재귀 호출을 금지하는 규칙은 스택 사용량을 예측 가능하게 만들기 위한 것이다.

```c
uint32_t factorial(uint32_t n) {
    if (n == 0U) {
        return 1U;
    }
    return n * factorial(n - 1U);
}
```

이 함수는 호출될 때마다 스택 프레임을 하나씩 쌓는다. 입력값이 커지면 호출 깊이가 깊어지고, 임베디드 시스템의 제한된 스택 공간을 넘어서면 스택 오버플로우(stack overflow)가 발생해 다른 변수나 반환 주소를 덮어쓰는 심각한 결함으로 이어질 수 있다. 데스크톱 환경에서는 스택이 수 메가바이트에 달해 문제가 드물지만, 마이크로컨트롤러의 스택은 보통 수 킬로바이트에 불과하다. MISRA C는 재귀를 금지하여 모든 함수의 최대 스택 사용량을 정적으로(실행 전에 코드 분석만으로) 계산할 수 있게 한다. 이는 WCET(최악 실행 시간) 분석과 마찬가지로, "최악의 경우에도 자원이 부족하지 않다"는 것을 실행 전에 증명하려는 접근이다.

동적 메모리 할당 함수를 제한하는 규칙도 비슷한 이유에서 나온다. `malloc`과 `free`를 자유롭게 쓰면 메모리 단편화(fragmentation)가 누적되어, 장시간 운행 중 할당이 실패하는 상황이 생길 수 있다. 이 실패 시점은 예측하기 어렵고, 재현도 어렵다. 그래서 많은 안전 critical 코드는 동적 할당을 금지하고 모든 메모리를 컴파일 시점이나 초기화 시점에 고정 배열로 확보해 둔다.

조건문에서 암묵적인 불(boolean) 변환을 금지하는 규칙도 흔히 등장한다.

```c
if (status_flags) {
    handle_error();
}
```

`status_flags`가 정수형 비트 플래그라면, 이 조건문은 "0이 아니면 참"이라는 C의 암묵 규칙에 의존한다. 코드 작성자가 "플래그가 1일 때만" 들어가길 의도했는데 실제로는 여러 비트의 조합이 true로 평가되어 의도와 다르게 동작할 수 있다. MISRA C는 불 값으로 쓰일 변수와 산술 연산에 쓰일 변수를 명확히 구분해, `if ((status_flags & ERROR_BIT) != 0U)`처럼 의도를 코드에 드러내도록 요구한다.

<details><summary><b>심화: decidable 규칙과 undecidable 규칙, 그리고 정적 분석의 한계</b></summary>

정적 분석 도구는 소스 코드를 실행하지 않고도 코드를 분석해 위반 여부를 판단한다. decidable 규칙(예: goto 사용 금지)은 코드의 구문 구조만 보면 100% 정확하게 위반 여부를 판정할 수 있다. 반면 undecidable 규칙(예: "모든 경로에서 변수가 사용 전에 초기화되는가")은 이론 전산학의 정지 문제(halting problem)와 비슷한 근본적 한계에 부딫힌다. 모든 가능한 실행 경로와 입력값의 조합을 완전히 분석하는 것은 일반적으로 불가능하기 때문이다.

그래서 undecidable 규칙에 대해 정적 분석 도구는 보수적인(conservative) 전략을 쓴다. "확실한 위반"과 "위반일 가능성이 있어 사람이 확인해야 하는 경고"를 구분하고, 애매한 경우는 안전한 방향으로, 즉 놓치기보다는 과잉 경고(false positive)를 내는 방향으로 판정한다. 이 때문에 실제 MISRA C 준수 작업에서는 도구가 낸 경고 중 상당수를 사람이 직접 검토해 "실제 위반"인지 "오탐"인지 분류하는 과정이 필요하며, 이 분류와 그 근거를 기록하는 것이 바로 다음 섹션에서 다룰 일탈(deviation) 관리의 핵심이다.

## 정적 분석과 준수 매트릭스, 일탈 관리

MISRA C 규칙은 수백 개에 달하기 때문에, 사람이 눈으로 모든 코드를 검토해 위반을 찾는 것은 현실적이지 않다. 그래서 실제 개발에서는 정적 분석(static analysis) 도구를 빌드 파이프라인에 통합해 자동으로 검사한다. 정적 분석 도구는 소스 코드를 파싱해 추상 구문 트리(abstract syntax tree)를 만들고, 각 규칙에 대응하는 패턴을 트리 위에서 탐색해 위반 지점을 보고한다.

프로젝트는 적용한 규칙 전체에 대해 각 규칙이 "준수되었는지", "일탈(deviation)되었는지", "해당 프로젝트에 적용되지 않는지"를 정리한 준수 매트릭스(compliance matrix)를 유지한다. 모든 Required 규칙을 예외 없이 지키는 프로젝트는 드물다. 때로는 특정 하드웨어의 레지스터 접근처럼 MISRA C 규칙과 충돌하지만 기술적으로 불가피한 코드가 있을 수 있다. 이런 경우 다음 절차를 거쳐 일탈을 문서화한다.

- 위반 코드의 위치와 해당 규칙을 명시한다.
- 왜 규칙을 지킬 수 없는지, 또는 왜 지키지 않는 것이 더 안전한지 기술적 근거를 작성한다.
- 위반으로 인해 생길 수 있는 위험을 어떻게 다른 방식으로 완화했는지(예: 추가 검증 코드, 리뷰 강화) 기록한다.
- 이 일탈 기록을 리뷰어가 승인한다.

이렇게 기록된 일탈은 사라지는 것이 아니라 프로젝트 문서의 일부가 되어, 나중에 감사(audit)나 안전 인증 과정에서 "왜 이 부분이 표준을 벗어났는가"를 추적할 수 있는 근거가 된다. 이는 이후 배울 ISO 26262의 추적성(traceability) 요구사항과도 맞닿아 있다. ISO 26262는 소프트웨어 단위 설계와 구현 단계에서 "강력한 타입 지정과 적절한 언어 부분집합 사용"을 권고하는데, MISRA C는 바로 그 권고를 C 언어에 대해 구체적으로 구현한 산업 표준으로 널리 인정받는다. 마찬가지로 안전하지 않은 코딩 패턴은 보안 취약점으로 이어지기도 쉬워서, 뒤에서 다룰 ISO/SAE 21434의 보안 코딩 요구사항에서도 MISRA C 준수가 자주 참조된다.

**확인 문제.** 다음 코드에서 발생할 수 있는 문제를 MISRA C의 관점에서 설명하라.

```c
int8_t level;
uint8_t raw = 200U;
level = raw;
if (level) {
    activate();
}
```

<details><summary>답 보기</summary>

첫 번째 문제는 `uint8_t`(0 ~ 255) 값인 200을 `int8_t`(-128 ~ 127)에 대입하는 부분이다. 200은 `int8_t`의 표현 범위를 벗어나므로 이 대입의 결과는 구현 정의 동작이 되어, 컴파일러나 플랫폼에 따라 `level`에 들어갈 실제 값이 달라질 수 있다. 두 번째 문제는 `if (level)`처럼 정수형 변수를 암묵적으로 불(boolean)로 취급하는 부분이다. `level`이 음수든 양수든 0이 아니기만 하면 참으로 평가되므로, 작성자가 "활성화 플래그가 설 때만"을 의도했더라도 실제로는 의도와 다른 범위의 값에서도 조건이 참이 될 수 있다. MISRA C를 따른다면 명시적인 범위 검사를 거쳐 타입을 맞추고, 조건문도 `if (level != 0)`처럼 비교 연산으로 의도를 명확히 드러내야 한다.

</details>

**확인 문제.** 어떤 팀이 재귀로 작성된 트리 탐색 함수가 MISRA C의 재귀 금지 규칙(Required)에 위반된다는 것을 알면서도, 일정 문제로 반복문으로 바꾸지 않고 그대로 출시하려 한다. MISRA C 프로세스상 이것이 허용되려면 어떤 절차가 필요한가?

<details><summary>답 보기</summary>

재귀 금지 규칙이 Mandatory가 아니라 Required 등급이라면, 기술적으로 타당한 근거와 문서화를 거쳐 일탈(deviation)로 처리하는 것이 절차적으로는 가능하다. 다만 "일정이 부족하다"는 이유만으로는 정당한 기술적 근거가 되지 못한다. 실제로 허용되려면 예를 들어 "탐색 대상 트리의 최대 깊이가 설계상 N으로 제한되어 있어 스택 사용량이 계산 가능하고 한계 내에 있다"는 식의 구체적 분석, 그 분석을 뒷받침하는 테스트나 정적 분석 결과, 그리고 리뷰어의 승인과 문서화가 모두 필요하다. 이런 근거 없이 위반을 넘기는 것은 MISRA C 준수 프로세스의 의도를 벗어난 것이며, 실제 안전 인증 심사에서도 받아들여지지 않을 가능성이 크다.

</details>

## 정리

- C 언어는 정의되지 않은 동작, 구현 정의 동작, 불특정 동작을 허용하는 범용 언어로, 안전 critical 시스템에는 그 자체로 위험 요소를 내포한다.
- MISRA C는 C 언어 중 위험하거나 모호한 부분을 제외한 안전한 부분집합을 사용하도록 규정하는 코딩 표준이다.
- 요구사항은 지침(Directive)과 규칙(Rule)으로 나뉘고, 규칙은 다시 decidable·undecidable로, 강도는 Mandatory·Required·Advisory로 분류된다.
- 타입 변환 제한, 재귀 금지, 동적 할당 제한, 암묵적 불 변환 금지 같은 대표 규칙들은 모두 "결과를 예측 가능하게 만든다"는 공통 목표를 가진다.
- 정적 분석 도구로 규칙 위반을 자동 검출하고, 불가피한 위반은 일탈(deviation) 절차를 거쳐 근거와 함께 문서화한다.

MISRA C는 C 언어라는 강력하지만 위험한 도구를, 안전과 보안이 중요한 자동차 소프트웨어에 맞게 다듬는 규율이다. 이 규율 자체가 사고를 막아주는 것은 아니지만, "표준이 보장하지 않는 동작에 의존하는 코드"를 체계적으로 걸러냄으로써 다음에 배울 검증·테스트 단계에서 드러나는 결함의 수를 크게 줄여준다.

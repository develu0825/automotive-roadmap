# AOSP 빌드 · 구조

차량용 IVI(In-Vehicle Infotainment) 헤드유닛이나 디지털 클러스터에 안드로이드를 올린다고 할 때, 우리가 스마트폰에서 쓰는 것과 똑같은 안드로이드를 그대로 설치할 수는 없습니다. 스마트폰의 안드로이드는 구글 플레이스토어와 구글 모바일 서비스(GMS)가 포함된 상용 빌드이고, 특정 제조사의 특정 칩셋에 맞춰 이미 완성되어 있는 결과물입니다. 차량 플랫폼은 그와 다릅니다. 차량 SoC(System on Chip) 벤더가 제공하는 보드, 두 개 이상의 디스플레이(클러스터와 IVI), 차량 전용 센서와 버스를 조합해야 하기 때문에, 구글이 공개한 AOSP(Android Open Source Project) 소스 코드를 직접 받아서 그 하드웨어에 맞게 새로 빌드해야 합니다.

`kernel-intro` 레슨에서 리눅스 커널과 디바이스 드라이버가 하드웨어를 어떻게 다루는지 다루었습니다. AOSP는 바로 그 커널 위에 올라가는 안드로이드 자체의 소프트웨어 스택입니다. 커널이 하드웨어를 관리한다면, AOSP는 그 위에서 앱을 실행하고 화면을 그리고 시스템 서비스를 띄우는 전체 소프트웨어 계층을 구성합니다. 이 레슨에서는 안드로이드 내부가 어떤 계층으로 쌓여 있는지, 그 소스를 어떻게 통째로 내려받는지, 그리고 어떤 명령으로 실제 이미지를 빌드해 내는지를 순서대로 살펴봅니다.

이 레슨에서 익히는 계층 구조와 빌드 흐름은 이후 Android Automotive OS(AAOS) 자체의 구성, VHAL(Vehicle HAL)을 통한 차량 신호 연동, CarService와 AIDL 기반 카 프레임워크(car-framework)를 다루는 레슨들의 토대가 됩니다. 지금 당장 모든 세부사항을 외울 필요는 없지만, "AOSP는 몇 개의 층으로 나뉘어 있고, 그 층들을 어떤 도구로 받아서 빌드하는가"라는 큰 그림만큼은 확실하게 잡고 넘어가야 합니다.

## 학습 목표

- 안드로이드 소프트웨어 스택을 커널부터 애플리케이션까지 계층별로 설명할 수 있다.
- Treble 아키텍처가 system 파티션과 vendor 파티션을 왜, 어떻게 분리하는지 이해한다.
- HAL(Hardware Abstraction Layer)이 HIDL에서 AIDL 기반으로 옮겨가는 흐름을 큰 틀에서 설명할 수 있다.
- `repo` 도구와 manifest 파일로 AOSP 소스를 내려받는 절차를 익힌다.
- `lunch`와 `m`을 이용해 빌드 타겟을 고르고 이미지를 빌드하는 과정을 이해한다.
- 부트로더부터 런처가 뜨기까지의 부팅 과정을 한 줄로 그릴 수 있다.

## 안드로이드 계층 구조: 커널에서 애플리케이션까지

안드로이드는 한 덩어리의 소프트웨어가 아니라, 역할이 분명한 여러 층이 쌓여 올라간 구조입니다. 가장 아래부터 순서대로 보면 다음과 같습니다.

- 리눅스 커널(Linux Kernel): 프로세스 스케줄링, 메모리 관리, 디바이스 드라이버를 담당합니다. 차량 SoC 벤더가 제공하는 보드 지원 패키지(BSP)가 이 층에 들어옵니다.
- HAL(Hardware Abstraction Layer): 커널 위에서 하드웨어 기능을 표준화된 인터페이스로 상위 계층에 노출합니다. 카메라, 센서, 디스플레이, 오디오 등 장치별로 HAL 모듈이 나뉘어 있습니다.
- 네이티브 라이브러리와 런타임: C/C++로 작성된 시스템 라이브러리(예: libc, 그래픽 엔진)와 ART(Android Runtime)가 이 층에 있습니다. ART는 앱의 바이트코드를 실제 기기에서 실행 가능한 코드로 변환하고 관리합니다.
- 프레임워크(Framework): 자바/코틀린으로 작성된 Java API와 `system_server`가 여기 속합니다. 액티비티 매니저, 윈도우 매니저, 패키지 매니저 같은 핵심 시스템 서비스가 `system_server` 프로세스 안에서 돌아갑니다.
- 애플리케이션(Application): 사용자가 직접 실행하는 앱 계층입니다. 차량이라면 클러스터 UI, IVI 런처, 내비게이션 앱 등이 이 층에 올라갑니다.

이 계층 구조를 이해하면, "커널 드라이버를 고쳤는데 왜 앱까지 다시 빌드해야 하지?" 혹은 반대로 "프레임워크 자바 코드만 고쳤는데 커널은 안 건드려도 되는 이유" 같은 질문에 답할 수 있습니다. 각 층은 그 아래 층이 제공하는 인터페이스에만 의존하도록 설계되어 있습니다.

## Treble 아키텍처: vendor와 system의 분리

안드로이드 초기에는 프레임워크와 벤더(SoC 제조사, 차량 OEM)가 만든 구현이 한 덩어리로 얽혀 있어서, 안드로이드 프레임워크 버전을 올릴 때마다 벤더 쪽 코드도 전부 다시 맞춰야 했습니다. 이를 해결하기 위해 구글은 Project Treble을 도입해 파티션을 구조적으로 분리했습니다.

- system 파티션: 구글이 배포하는 안드로이드 프레임워크 코드가 들어갑니다. OEM이나 SoC 벤더와 무관하게 공통으로 관리됩니다.
- vendor 파티션: SoC 벤더나 차량 OEM이 만든 HAL 구현, 드라이버 관련 바이너리가 들어갑니다.

두 파티션이 분리되어 있으면, 안드로이드 프레임워크를 새 버전으로 올릴 때 vendor 파티션을 그대로 둔 채로 system 파티션만 갈아끼우는 것이 가능해집니다. 이 둘 사이의 호환성을 보장하는 개념이 VINTF(Vendor Interface)입니다. VINTF는 system 쪽이 요구하는 인터페이스 버전과 vendor 쪽이 제공하는 인터페이스 버전이 서로 맞는지를 매니페스트 형태로 선언하고 검증합니다. 자동차 플랫폼처럼 한 번 양산된 차량의 소프트웨어를 몇 년에 걸쳐 업데이트해야 하는 환경에서는, 이렇게 프레임워크와 벤더 구현을 분리해 둔 구조가 특히 중요합니다.

<details><summary><b>심화: VINTF와 호환성 매트릭스</b></summary>

VINTF는 크게 두 종류의 정보를 다룹니다. 하나는 vendor 쪽이 "나는 이런 HAL들을 이 버전으로 구현하고 있다"고 선언하는 매니페스트(vendor manifest)이고, 다른 하나는 system 쪽이 "나는 이런 HAL 버전들을 필요로 한다"고 요구하는 호환성 매트릭스(compatibility matrix)입니다. 기기가 부팅할 때 이 두 정보를 비교해서 서로 맞지 않으면 부팅을 거부하거나 경고를 냅니다. 차량처럼 시스템 업데이트와 벤더 업데이트가 서로 다른 주기로 배포될 수 있는 환경에서, 이 검증 과정이 두 업데이트가 어긋나서 생기는 문제를 미리 걸러주는 역할을 합니다.

</details>

## HAL 인터페이스: HIDL에서 AIDL로

HAL은 프레임워크가 하드웨어 기능을 호출할 때 거치는 경계입니다. 초기 Treble 아키텍처에서는 이 경계에서 HIDL(HAL Interface Definition Language)이라는 전용 인터페이스 정의 언어를 사용했습니다. HIDL은 인터페이스를 `.hal` 파일로 정의하고, 이를 바탕으로 프록시/스텁 코드를 자동 생성해서 프레임워크 프로세스와 HAL 구현 프로세스가 서로 통신하게 했습니다.

이후 안드로이드는 프레임워크 내부에서 이미 널리 쓰이던 AIDL(Android Interface Definition Language)을 HAL 경계에서도 쓸 수 있도록 확장하는 방향으로 옮겨가고 있습니다. 이렇게 안정적인 버전 관리를 보장하도록 다듬어진 AIDL을 stable AIDL이라고 부르기도 합니다. 핵심은, 인터페이스 정의 언어가 하나로 통일되면 프레임워크 내부 서비스든 HAL 경계든 같은 방식으로 인터페이스를 선언하고 버전을 관리할 수 있다는 점입니다. 버전별로 어떤 HAL이 HIDL에서 AIDL로 완전히 옮겨갔는지는 안드로이드 버전마다 다르므로, 이 레슨에서는 "HIDL에서 AIDL로 이동하는 큰 흐름이 있다"는 수준으로 이해하고, 실제 작업 시에는 해당 안드로이드 버전의 공식 문서를 확인하는 것이 안전합니다.

```
# HAL 인터페이스 정의 파일 위치 예시 (버전/경로는 소스 트리마다 다를 수 있음)
hardware/interfaces/   # HIDL 시절 인터페이스 정의가 모이는 위치
system/hardware/interfaces/   # AIDL 기반 인터페이스가 자리하는 위치의 예
```

## 소스 코드 받기: repo와 manifest

AOSP는 하나의 거대한 Git 저장소가 아니라, 커널, 프레임워크, 각종 라이브러리, 빌드 시스템이 각각 독립된 Git 저장소로 나뉘어 있고 그 수가 수십 개에서 수백 개에 이릅니다. 이걸 사람이 일일이 `git clone` 하는 것은 현실적이지 않기 때문에, 구글은 `repo`라는 멀티 Git 저장소 관리 도구를 만들었습니다.

`repo`는 manifest라는 XML 파일을 기준으로 동작합니다. manifest에는 "어떤 저장소를, 어떤 브랜치로, 어느 경로에 받을 것인가"가 정의되어 있습니다. 차량 SoC 벤더가 자체 BSP와 벤더 코드를 추가로 배포할 때도, 보통 구글 공식 manifest에 벤더 전용 저장소 목록을 더한 로컬 manifest 형태로 제공합니다.

```
# repo 초기화: manifest 저장소와 브랜치 지정
repo init -u https://android.googlesource.com/platform/manifest -b android-14.0.0_r1

# manifest에 정의된 모든 저장소 동기화 (수십 개 저장소를 병렬로 내려받음)
repo sync -j8
```

`repo sync`가 끝나면 소스 트리 전체가 로컬에 준비됩니다. 이 상태에서 비로소 빌드를 시작할 수 있습니다.

## 빌드 시스템: Soong, lunch, m

AOSP의 빌드 시스템은 과거 Make 기반(Android.mk 파일)으로 모듈을 정의했지만, 현재는 Soong이라는 빌드 시스템으로 점차 넘어가는 중입니다. Soong은 Blueprint라는 메타 빌드 프레임워크 위에서 동작하고, 각 모듈은 Android.mk 대신 Android.bp 파일로 선언적으로 기술합니다. Android.mk가 스크립트처럼 절차적으로 빌드 규칙을 적는 방식이었다면, Android.bp는 모듈의 이름, 소스 파일, 의존성 같은 속성을 JSON과 비슷한 형태로 선언하는 방식입니다. 선언적 정의는 분석과 병렬 빌드 최적화가 더 쉬워서, AOSP는 점진적으로 Android.mk를 Android.bp로 옮겨가고 있습니다.

실제로 빌드를 시작하려면 먼저 어떤 제품(product)을, 어떤 빌드 타입(variant)으로 빌드할지 선택해야 합니다. 이 선택을 하는 명령이 `lunch`입니다.

```
# 환경 설정 스크립트 로드
source build/envsetup.sh

# 빌드 타겟 선택: <제품>-<빌드타입> 형식
lunch aosp_arm64-userdebug

# 실제 빌드 실행
m -j8
```

`lunch aosp_arm64-userdebug`에서 `aosp_arm64`는 타겟 하드웨어 아키텍처를 포함한 제품 구성이고, `userdebug`는 빌드 타입입니다. 빌드 타입은 세 가지가 있습니다.

- user: 실제 출시용 빌드입니다. 루트 쉘 접근이 막혀 있고 디버깅 기능이 최소화되어 있습니다.
- userdebug: user와 거의 동일하지만 루트 권한과 디버깅 도구에 접근할 수 있어서, 양산 직전 단계의 개발·검증에 많이 쓰입니다.
- eng: 엔지니어링 빌드로, 디버깅 도구와 추가 도구가 가장 폭넓게 포함되어 개발 초기 단계에 주로 사용됩니다.

차량 프로젝트에서는 실제 양산 직전까지 대부분 userdebug로 개발하다가, 최종 출시 직전에 user 빌드로 전환해 검증하는 흐름이 일반적입니다.

<details><summary><b>심화: 빌드 타입을 잘못 고르면 생기는 문제</b></summary>

user 빌드는 adb root 같은 디버깅 경로가 막혀 있어서, 개발 중인 클러스터 UI나 VHAL 연동 코드를 단계별로 디버깅하기가 매우 어렵습니다. 반대로 eng 빌드를 그대로 양산 차량에 올리면 불필요한 디버깅 인터페이스와 로그가 살아 있어 보안과 성능 양쪽에 문제가 될 수 있습니다. 그래서 실제 차량 프로젝트에서는 개발용 ECU(또는 벤치 보드)에는 userdebug나 eng을, 실차 검증 및 양산 단계에는 user 빌드를 올리는 식으로 단계별로 빌드 타입을 바꿔가며 진행합니다.

</details>

## 부팅 과정으로 보는 전체 그림

지금까지 다룬 계층 구조와 빌드 결과물이 실제 기기에서 어떻게 살아나는지는 부팅 과정을 따라가 보면 가장 잘 보입니다.

- 부트로더(Bootloader): 전원이 들어오면 가장 먼저 실행되어, 커널 이미지를 메모리에 올리고 실행을 넘깁니다.
- 커널(Kernel): 하드웨어를 초기화하고 디바이스 드라이버를 로드한 뒤, 최초의 사용자 공간 프로세스인 init을 실행합니다.
- init 프로세스: `init.rc` 같은 설정 파일을 읽어서 시스템 서비스들을 순서대로 시작합니다. HAL 데몬들도 이 단계에서 많이 올라옵니다.
- Zygote: 앱 프로세스를 만들기 위한 템플릿 프로세스입니다. ART와 핵심 프레임워크 클래스를 미리 로드해 둔 상태에서 `fork()`로 복제되기 때문에, 매번 새 앱을 완전히 처음부터 초기화하지 않고도 빠르게 새 앱 프로세스를 띄울 수 있습니다.
- system_server: Zygote에서 포크되어 나온 특별한 프로세스로, 액티비티 매니저, 윈도우 매니저, 패키지 매니저 등 프레임워크의 핵심 서비스를 이 프로세스 안에서 구동합니다.
- 런처(Launcher): system_server가 준비를 마치면 비로소 런처 앱이 실행되어 사용자가 보는 첫 화면이 뜹니다.

차량이라면 이 마지막 단계에서 클러스터용 디스플레이와 IVI용 디스플레이가 각각 다른 화면 구성으로 동시에 떠야 합니다. 같은 system_server와 Zygote 위에서, 디스플레이별로 서로 다른 액티비티 스택과 UI를 띄우는 멀티 디스플레이 구성이 필요해지는데, 이 부분의 구체적인 구현은 이후 Android Automotive OS 레슨에서 다룹니다.

init 프로세스가 읽는 `init.rc` 파일은 사실 여러 개로 나뉘어 있습니다. 코어 안드로이드가 공통으로 쓰는 `init.rc` 외에, 특정 하드웨어나 보드에만 필요한 서비스는 벤더 쪽에서 별도의 `.rc` 파일로 추가합니다. 예를 들어 차량 SoC 벤더가 제공하는 CAN 통신 데몬을 부팅 초기에 띄우고 싶다면, 아래와 같은 형태로 서비스를 선언해 둘 수 있습니다.

```
# vendor/vehicle_bsp/init.vehicle.rc (개념 예시)
service can-gateway /vendor/bin/can-gatewayd
    class core
    user system
    group system
    oneshot
```

`class core`는 이 서비스가 시스템의 핵심 서비스 그룹에 속한다는 뜻이고, `oneshot`은 한 번 실행되고 나면 자동으로 재시작하지 않는다는 의미입니다. 이렇게 init이 처리하는 서비스 선언 하나하나가, 앞서 본 계층 구조에서 "커널이 하드웨어를 초기화한 뒤 그 위에서 어떤 유저공간 프로세스들이 어떤 순서로 올라오는지"를 구체적으로 보여 주는 지점입니다. 이 서비스 선언과 유저공간 프로세스 관리 방식은 이후 유저공간·IPC 레슨에서 다루는 내용과도 자연스럽게 이어집니다.

<details><summary><b>심화: Zygote가 앱 실행을 빠르게 만드는 이유</b></summary>

새 앱을 실행할 때마다 ART 런타임을 처음부터 초기화하고 공통 프레임워크 클래스를 전부 로드한다면, 매번 적지 않은 시간이 걸릴 것입니다. Zygote는 이런 공통 초기화를 미리 한 번만 해 둔 상태로 대기하다가, 새 앱이 필요할 때 `fork()` 시스템 콜로 그 메모리 상태를 복제해서 새 프로세스를 만듭니다. 복제된 직후에는 부모와 자식이 메모리 페이지를 공유하다가(copy-on-write), 자식이 실제로 뭔가를 쓰기 시작할 때만 그 페이지가 복사됩니다. 이 덕분에 앱 하나를 새로 띄우는 비용이 "안드로이드 런타임을 처음부터 띄우는 비용"이 아니라 "이미 떠 있는 프로세스를 가볍게 복제하는 비용"으로 줄어듭니다.

</details>

**확인 문제.** Treble 아키텍처가 system 파티션과 vendor 파티션을 분리한 이유는 무엇이며, 두 파티션 사이의 호환성은 어떤 개념으로 보장되는가?

<details><summary>답 보기</summary>

프레임워크(system)와 벤더 구현(vendor)이 한 덩어리로 얽혀 있으면 안드로이드 프레임워크 버전을 올릴 때마다 벤더 쪽 코드도 전부 다시 맞춰야 합니다. Treble은 이 둘을 별도 파티션으로 분리해, system 쪽만 교체해도 vendor 쪽은 그대로 둘 수 있게 했습니다. 이 둘 사이의 인터페이스 버전이 서로 맞는지는 VINTF(Vendor Interface)가 vendor manifest와 호환성 매트릭스를 비교해 검증합니다.

</details>

**확인 문제.** `lunch aosp_arm64-userdebug` 다음에 `m`을 실행하기 전, `repo sync`가 먼저 필요한 이유는 무엇인가?

<details><summary>답 보기</summary>

AOSP 소스는 하나의 저장소가 아니라 수십 개의 독립된 Git 저장소로 나뉘어 있습니다. `repo sync`는 manifest 파일에 정의된 모든 저장소를 한 번에 동기화해서 소스 트리 전체를 로컬에 준비하는 단계입니다. 이 단계가 끝나기 전에는 `lunch`로 타겟을 선택해도 빌드할 소스 자체가 갖춰져 있지 않으므로 `m`이 정상적으로 동작할 수 없습니다.

</details>

## 정리

AOSP는 리눅스 커널 위에 HAL, 네이티브 라이브러리/런타임, 프레임워크, 애플리케이션이 차례로 쌓인 계층 구조이며, Treble 아키텍처가 system과 vendor 파티션을 분리해 프레임워크와 벤더 구현을 독립적으로 관리할 수 있게 해 줍니다. HAL 경계의 인터페이스 정의는 HIDL에서 AIDL 기반으로 옮겨가는 흐름 속에 있습니다. 실제 빌드는 `repo`와 manifest로 수십 개 저장소를 받아 오고, Soong(Android.bp) 기반 빌드 시스템에서 `lunch`로 타겟을 고른 뒤 `m`으로 이미지를 만드는 순서로 진행됩니다. 부트로더, 커널, init, Zygote, system_server, 런처로 이어지는 부팅 과정은 이 모든 계층이 실제 기기에서 어떤 순서로 살아나는지를 보여 줍니다. 이 큰 그림은 이후 차량 전용 안드로이드 구성, 차량 신호 연동, 카 프레임워크 레슨으로 이어지는 토대가 됩니다.

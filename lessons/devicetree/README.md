# 디바이스 트리

같은 차종의 인포테인먼트 보드라도, 저가형 트림과 고급형 트림은 탑재된 카메라 개수나 터치스크린 컨트롤러 종류가 다를 수 있다. 똑같은 SoC(System on Chip)를 쓰면서도 그 주변에 어떤 센서와 커넥터가 연결되어 있는지는 보드마다 다른 것이다. 만약 "이 보드에는 I2C 버스의 0x48번 주소에 온도 센서가 있고, SPI 버스에는 터치 컨트롤러가 있다"는 정보를 커널 소스 코드 안에 직접 하드코딩한다면 어떻게 될까. 트림이 하나 더 추가될 때마다 커널 소스 코드를 고치고 다시 빌드해야 하고, 심지어 완전히 다른 보드마다 서로 다른 커널 이미지를 따로 관리해야 한다. 리눅스 커널이 전 세계 수천 종의 ARM 보드를 지원하면서도 이런 혼란에 빠지지 않을 수 있었던 비결이 바로 디바이스 트리(device tree)다.

디바이스 트리는 "이 보드에는 어떤 하드웨어가, 어떤 주소에, 어떤 설정으로 연결되어 있는가"를 커널 소스 코드가 아니라 별도의 데이터 파일로 표현하는 방식이다. 커널 바이너리 자체는 모든 보드에 대해 똑같은 하나의 이미지로 유지하고, 각 보드마다 다른 하드웨어 구성 정보만 디바이스 트리라는 작은 파일에 따로 적어서 부팅 시점에 커널에게 건네준다. 이는 마치 같은 모델의 가전제품이라도 국가마다 다른 전압과 플러그 규격에 맞춰 전원 어댑터만 따로 갈아 끼우는 것과 비슷하다. 가전제품의 핵심 회로(커널)는 그대로 두고, 그 주변 환경에 맞는 설명서(디바이스 트리)만 바꿔 끼우는 셈이다.

앞 레슨에서 U-Boot가 커널을 실행시킬 때 디바이스 트리 이미지의 주소를 레지스터에 담아 전달한다는 것을 보았다. 이번 레슨에서는 이 디바이스 트리가 실제로 어떤 문법으로 작성되고, 그 문법이 어떻게 실제 하드웨어 주소와 연결되며, 커널이 이 정보를 어떻게 활용해 올바른 드라이버를 연결하는지를 살펴본다.

## 학습 목표

- 디바이스 트리가 왜 필요한지와, 이것이 없던 시절 커널이 겪었던 문제가 무엇인지 설명할 수 있다.
- DTS(Device Tree Source) 파일의 노드와 속성 문법을 읽고, 간단한 디바이스 트리를 직접 작성할 수 있다.
- `compatible` 속성이 커널의 드라이버와 하드웨어 노드를 어떻게 연결시키는지 설명할 수 있다.
- `reg`, `interrupts`, phandle 참조 같은 핵심 속성이 각각 어떤 정보를 표현하는지 설명할 수 있다.
- DTS가 DTB(Device Tree Blob)로 컴파일되는 과정과, 디바이스 트리 오버레이(overlay)의 개념을 설명할 수 있다.

## 하드코딩의 문제: 디바이스 트리 이전의 세계

디바이스 트리가 리눅스 커널에 본격적으로 도입되기 전에는, 각 보드를 지원하는 코드를 커널 소스 코드 안에 `arch/arm/mach-xxx` 같은 디렉터리에 C 코드로 직접 작성했다. 이 코드 안에는 "이 보드의 UART 컨트롤러는 물리 주소 0xFE201000에 있다", "이 보드의 온도 센서는 I2C 1번 버스의 0x48번 주소에 있다" 같은 정보가 숫자 그대로 박혀 있었다. 이 방식의 가장 큰 문제는 확장성이었다. 새로운 보드가 하나 나올 때마다 그 보드만을 위한 C 코드 파일이 하나 더 늘어났고, 리눅스 커널 소스 트리 안에는 수천 개의 거의 비슷하지만 조금씩 다른 보드 지원 파일이 쌓여갔다. 보드 하나에 작은 변경(예를 들어 센서 주소가 바뀌는 리비전)이 생길 때마다 커널 전체를 다시 빌드해야 했고, 이는 커널 코드와 하드웨어 구성 정보가 지나치게 뒤섞여 있다는 근본적인 설계 문제였다.

디바이스 트리는 이 둘을 분리한다. 커널은 "I2C 버스에서 어떤 주소에 있는 장치든, 그 장치가 특정 종류라고 선언되어 있으면 해당 드라이버를 연결하라"는 일반적인 규칙만 가지고 있고, "이 보드에는 실제로 그 장치가 몇 번 주소에 있는가"라는 구체적인 사실은 디바이스 트리 파일에 둔다. 똑같은 커널 바이너리가 디바이스 트리 파일만 바꿔 끼우면 전혀 다른 보드 위에서도 올바르게 동작할 수 있게 되는 것이다.

## DTS 문법: 노드와 속성으로 하드웨어 그리기

디바이스 트리는 사람이 읽을 수 있는 텍스트 형태의 소스 파일, 즉 DTS(Device Tree Source, `.dts` 확장자)로 작성된다. DTS는 하드웨어 구성을 나무(tree) 구조로 표현하는데, 각 하드웨어 구성요소는 노드(node)로 표현되고, 그 노드가 가진 특징은 속성(property)으로 표현된다. 간단한 예시를 보자.

```
/ {
    compatible = "acme,vehicle-ivi-board";

    i2c@7e804000 {
        compatible = "arm,pl011-i2c";
        reg = <0x7e804000 0x1000>;
        #address-cells = <1>;
        #size-cells = <0>;

        temp_sensor@48 {
            compatible = "ti,tmp102";
            reg = <0x48>;
            interrupt-parent = <&gic>;
            interrupts = <0 45 4>;
        };
    };

    leds {
        compatible = "gpio-leds";
        status_led {
            label = "status";
            gpios = <&gpio 17 0>;
        };
    };
};
```

맨 위의 `/ { ... }`는 전체 트리의 루트 노드다. 그 안에 중첩된 `i2c@7e804000` 같은 이름은 노드의 레이블과 그 노드가 위치한 주소를 함께 나타내는 관례적인 표기이며, `@` 뒤의 숫자는 보통 그 하드웨어의 레지스터 시작 주소와 같다. `i2c@7e804000` 노드 안에 다시 `temp_sensor@48`이라는 자식 노드가 들어 있는 것은, 이 온도 센서가 바로 위 I2C 버스에 연결된 장치라는 물리적인 연결 관계를 나무 구조 그대로 표현한 것이다.

`#address-cells`와 `#size-cells`는 조금 낯설지만 중요한 속성이다. 이 두 값은 "이 노드의 자식 노드들이 가지는 `reg` 속성을 몇 개의 32비트 정수(셀, cell)로 해석해야 하는가"를 선언한다. 예를 들어 `i2c@7e804000` 노드가 `#address-cells = <1>;`과 `#size-cells = <0>;`을 가지고 있다는 것은 "내 자식 노드들의 `reg`는 주소 1개짜리 셀로만 표현되고, 크기는 아예 표현하지 않는다"는 뜻이다. 실제로 그 자식인 `temp_sensor@48`의 `reg = <0x48>;`는 숫자 하나뿐이다. 이는 I2C 버스의 특성과 맞아떨어진다. I2C에서는 각 장치가 7비트 또는 10비트의 짧은 주소 하나만으로 식별되고, "그 장치가 메모리에서 몇 바이트를 차지하는가" 같은 크기 개념 자체가 의미가 없기 때문이다. 반면 메모리 버스처럼 "시작 주소와 그 범위" 둘 다 필요한 경우에는 `#address-cells = <1>;`과 `#size-cells = <1>;`을 함께 써서, 자식 노드의 `reg`가 "주소, 크기" 두 값의 쌍으로 해석되도록 지정한다. 이 설정이 부모와 자식 사이에서 일치하지 않으면 DTC 컴파일러가 `reg` 값을 엉뚱하게 잘못 해석해, 겉보기에 숫자는 맞게 적었는데도 커널이 하드웨어의 주소나 크기를 완전히 다른 값으로 읽어버리는 문제가 생긴다.

가장 중요한 속성은 `compatible`이다. 이는 "이 노드가 실제로 어떤 종류의 하드웨어인가"를 문자열로 선언하며, 보통 "제조사,모델명" 형식을 따른다. 커널은 부팅 과정에서 디바이스 트리를 순회하며 각 노드의 `compatible` 문자열을 읽고, 자신이 가지고 있는 드라이버들 중 그 문자열과 일치하는 드라이버를 찾아 연결한다. 예를 들어 `compatible = "ti,tmp102"`라는 노드를 발견하면 커널은 `ti,tmp102` 문자열을 지원한다고 등록된 온도 센서 드라이버를 찾아 그 노드에 연결한다. `reg` 속성은 그 하드웨어가 어떤 메모리 주소(또는 버스 주소)에 있는지를 나타내며, I2C 자식 노드의 `reg = <0x48>;`처럼 버스 주소 하나만 표현하거나, 부모의 `reg = <0x7e804000 0x1000>;`처럼 "시작 주소와 그 크기" 두 값을 함께 표현할 수도 있다. `interrupts` 속성은 그 장치가 어떤 인터럽트 번호를 통해 CPU에게 이벤트를 알리는지를 나타내는데, 그 정확한 해석 방식은 `interrupt-parent`가 가리키는 인터럽트 컨트롤러 노드의 규칙에 따라 달라진다.

## phandle: 노드끼리 서로를 가리키는 법

디바이스 트리의 노드들은 나무 구조로 중첩되어 있지만, 때로는 나무 구조상 멀리 떨어진 두 노드가 서로를 참조해야 할 때가 있다. 위 예시의 `leds` 노드 아래 `status_led`가 가진 `gpios = <&gpio 17 0>;` 속성이 그런 경우다. `&gpio`는 어딘가 다른 곳에 `gpio: gpio@7e200000 { ... };`처럼 레이블이 붙어 정의된 GPIO 컨트롤러 노드를 가리키는 참조다. 이렇게 `&레이블` 형태로 다른 노드를 가리키는 것을 phandle(phandle, 포인터 핸들) 참조라 부른다. DTS를 컴파일할 때는 이 `&gpio` 같은 레이블이 내부적으로 고유한 정수 식별자로 바뀌고, 최종 바이너리에서는 그 정수값으로 노드 간의 연결 관계가 저장된다. 이 메커니즘 덕분에 GPIO 컨트롤러, 인터럽트 컨트롤러, 클럭 소스처럼 여러 장치가 공통으로 참조해야 하는 자원을 중복 없이 한 번만 정의하고, 필요한 모든 곳에서 그 노드를 가리키기만 하면 된다.

## DTS에서 DTB로: 컴파일과 부팅 시점의 활용

사람이 작성한 텍스트 형식의 DTS 파일은 커널이 부팅 중에 빠르게 파싱할 수 있는 것이 아니다. 그래서 빌드 과정에서 DTC(Device Tree Compiler)라는 도구가 DTS를 DTB(Device Tree Blob)라는 컴팩트한 이진 형식으로 변환한다. 이 변환 과정은 앞서 배운 "C 소스 코드를 기계어로 번역하는" 컴파일 과정과 비슷한 위치에 있다고 생각하면 된다.

```sh
dtc -I dts -O dtb -o vehicle-board.dtb vehicle-board.dts
```

앞 레슨에서 U-Boot가 이 `.dtb` 파일을 커널 이미지와 함께 DRAM에 읽어들이고, 그 메모리 주소를 레지스터에 담아 커널에게 넘겨준다고 설명했다. 커널은 실행을 시작하자마자 이 DTB를 파싱해서 메모리의 나무 구조를 복원하고, 그 안의 각 노드를 순회하며 `compatible` 문자열에 맞는 드라이버를 찾아 연결하는 과정을 거친다. 이렇게 해서 "커널 바이너리는 하나, 디바이스 트리는 보드마다 다르게"라는 설계가 실제로 작동하게 된다.

<details><summary><b>심화: 디바이스 트리 오버레이와 확장 모듈</b></summary>

메인 디바이스 트리 전체를 다시 작성하지 않고도, 특정 확장 모듈이나 애드온 보드를 추가하기 위해 기존 디바이스 트리의 일부에만 변경이나 추가를 적용하는 기법이 디바이스 트리 오버레이(device tree overlay)다. 예를 들어 같은 메인 보드에 "후방 카메라 모듈"이 꽂혀 있을 때만 필요한 노드를 추가하고 싶다면, 메인 보드의 DTS 전체를 복제해서 수정하는 대신, 오버레이 파일에 "이 레이블이 붙은 노드를 찾아서, 그 안에 이 자식 노드를 추가하라"는 형식으로 변경 사항만 기술한다.

```
/dts-v1/;
/plugin/;

&i2c1 {
    camera_module@30 {
        compatible = "acme,rear-camera";
        reg = <0x30>;
    };
};
```

오버레이는 보통 `/plugin/;` 지시자로 자신이 기본 트리가 아니라 그 위에 덧붙여지는 조각임을 선언하며, U-Boot나 커널의 부트 과정에서 `fdt apply` 같은 명령으로 기본 디바이스 트리에 병합된다. 이 기법은 라즈베리파이 같은 범용 임베디드 보드의 HAT(확장 보드) 생태계에서 널리 쓰이며, 자동차 분야에서도 동일한 메인 보드에 여러 센서 구성 옵션을 유연하게 조합해야 하는 상황에서 활용된다.

</details>

<details><summary><b>심화: U-Boot 단계와 커널 단계에서 디바이스 트리가 각각 하는 역할의 차이</b></summary>

흥미롭게도 디바이스 트리는 커널만 쓰는 것이 아니라, 앞 레슨에서 다룬 U-Boot 자신도 똑같은 디바이스 트리(또는 그 축약된 버전)를 참조해서 자신의 하드웨어 초기화에 활용하는 경우가 많다. 다만 U-Boot가 참조하는 디바이스 트리와 커널에게 최종적으로 전달되는 디바이스 트리가 항상 똑같은 파일인 것은 아니다. U-Boot는 부팅 과정에서 실제 하드웨어 상태를 확인해 얻은 정보(예를 들어 실제 장착된 DRAM 용량이나, 보드 리비전에 따라 달라지는 특정 핀 상태)를 바탕으로, 커널에게 넘겨주기 직전의 디바이스 트리 내용을 메모리 상에서 동적으로 수정(fix-up)하기도 한다.

예를 들어 같은 커널 이미지를 쓰더라도 DRAM이 2 GB 장착된 보드와 4 GB 장착된 보드가 있다면, U-Boot가 실제로 검출한 DRAM 크기를 디바이스 트리의 메모리 노드에 반영해 커널에게 넘겨줄 수 있다. 이렇게 하면 디바이스 트리 파일 자체를 여러 버전으로 따로 만들지 않고도, 하나의 디바이스 트리 소스가 실제 하드웨어의 미세한 차이에 맞춰 유연하게 조정될 수 있다.

</details>

**확인 문제.** 디바이스 트리가 없던 시절, 보드마다 커널 소스 코드 안에 하드웨어 주소를 직접 하드코딩했을 때 생겼던 근본적인 문제는 무엇이며, 디바이스 트리가 이를 어떻게 해결하는지 설명하라.
<details><summary>답 보기</summary>

하드웨어 구성 정보가 커널 소스 코드 안에 직접 섞여 있으면, 보드가 새로 나오거나 기존 보드의 리비전이 바뀔 때마다 커널 소스 코드 자체를 수정하고 다시 빌드해야 했다. 이는 보드 종류가 늘어날수록 유지해야 하는 커널 변형(또는 보드별 소스 파일)이 기하급수적으로 늘어나는 확장성 문제를 낳았고, 커널 코드와 특정 보드의 하드웨어 사실이 지나치게 결합되어 있다는 설계상 문제이기도 했다. 디바이스 트리는 하드웨어 구성 정보를 커널 바이너리와 분리된 별도의 데이터 파일(DTB)로 떼어내어, 똑같은 커널 바이너리가 디바이스 트리 파일만 바꿔 끼우면 다른 보드 위에서도 그대로 동작하도록 만든다. 결과적으로 보드가 추가되어도 커널을 다시 빌드할 필요 없이 새로운 디바이스 트리 파일만 추가하면 된다.

</details>

**확인 문제.** 어떤 디바이스 트리 노드에 `compatible = "ti,tmp102";`라는 속성이 있다고 하자. 커널이 부팅 과정에서 이 속성을 어떻게 활용해 올바른 드라이버를 연결하는지 설명하라.
<details><summary>답 보기</summary>

커널 안에는 여러 드라이버가 "나는 이러이러한 compatible 문자열을 가진 장치를 지원한다"고 자신을 등록해 둔 표(테이블)가 있다. 커널은 부팅 중 디바이스 트리를 순회하면서 각 노드의 `compatible` 속성 문자열을 읽고, 이 등록 표에서 똑같은 문자열("ti,tmp102")을 지원한다고 선언한 드라이버를 찾는다. 일치하는 드라이버를 찾으면, 커널은 그 드라이버의 초기화 함수(probe 함수)를 호출하면서 해당 노드의 나머지 속성들(`reg`로 표현된 버스 주소, `interrupts`로 표현된 인터럽트 번호 등)을 함께 넘겨준다. 드라이버는 이 정보를 받아 실제 그 주소의 하드웨어와 통신을 시작한다. 만약 일치하는 드라이버가 커널 안에 없다면, 그 노드는 연결되지 않은 채로 남아 해당 장치는 동작하지 않는다.

</details>

## 정리

- 디바이스 트리는 하드웨어 구성 정보를 커널 소스 코드에서 분리해, 똑같은 커널 바이너리가 디바이스 트리 파일만 바꿔 끼우면 여러 보드를 지원할 수 있게 해준다.
- DTS는 노드와 속성으로 하드웨어의 물리적 연결 관계를 나무 구조로 표현하며, `compatible`은 커널의 드라이버와 노드를 연결하는 핵심 속성이다.
- `reg`, `interrupts` 같은 속성은 하드웨어의 주소와 인터럽트 번호를 표현하고, phandle(`&레이블`) 참조는 나무 구조상 떨어진 노드들이 공통 자원을 공유하도록 연결해 준다.
- DTS는 DTC 컴파일러를 통해 DTB라는 이진 형식으로 변환되어 부팅 시점에 U-Boot가 커널에게 전달하며, 디바이스 트리 오버레이는 기본 트리의 일부만 추가/수정할 수 있게 해준다.

이번 레슨에서는 디바이스 트리가 어떻게 하드웨어 구성을 커널 바이너리와 분리해 표현하는지, 그리고 `compatible` 속성이 어떻게 드라이버와 노드를 연결하는지를 살펴보았다. 다음 레슨에서는 이렇게 준비된 부트로더와 디바이스 트리 지식을 바탕으로, 완전히 새로운 보드에 클럭과 핀 뮤잉, 전원 시퀀스까지 처음부터 세워 올리는 보드 브링업 과정을 다룬다.

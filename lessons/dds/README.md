# DDS

SOME/IP · SOA에서 서버가 서비스를 광고하고 클라이언트가 그 서비스를 찾아 연결을 맺는 구조를 배웠다. 이 방식은 "누가 이 데이터를 제공하는가"를 명확히 아는 1대1 관계(혹은 1대다 구독 관계)를 전제로 한다. 그런데 자율주행처럼 수십 개의 센서와 알고리즘 모듈이 서로의 출력을 입력으로 쓰는 복잡한 소프트웨어 그래프에서는, "이 데이터가 누구에게서 오고 누구에게 가는지"를 하나하나 설계 시점에 고정하는 것이 점점 더 부담스러워진다. 카메라 인식 모듈, 레이더 퓨전 모듈, 경로 계획 모듈, 제어 모듈이 서로 데이터를 주고받는데, 이 모듈들의 개수와 조합은 차종과 소프트웨어 버전에 따라 계속 달라질 수 있다.

이런 환경에서는 "데이터를 만드는 쪽"과 "데이터를 쓰는 쪽"이 서로의 존재를 전혀 몰라도 통신이 성립하는 구조가 유리하다. 발행자(publisher)는 그냥 "이런 종류의 데이터가 나왔다"고 토픽(topic)에 데이터를 뿌리고, 구독자(subscriber)는 "나는 이 토픽을 구독한다"고만 선언하면, 중간에서 데이터가 자동으로 흘러간다. 발행자가 몇 명인지, 구독자가 몇 명인지, 그들이 네트워크 어디에 있는지는 서로 알 필요가 없다. 이런 통신 방식을 발행/구독(publish/subscribe) 패턴이라 부르고, 이를 데이터 중심으로 표준화한 미들웨어가 DDS(Data Distribution Service)다.

DDS는 OMG(Object Management Group)가 표준화한 미들웨어로, 원래 항공·국방·산업 자동화처럼 수십에서 수백 개의 노드가 실시간으로 데이터를 주고받아야 하는 분야에서 먼저 쓰이기 시작했고, 이후 로봇 운영체제인 ROS 2의 기본 통신 계층으로 채택되면서 자율주행 소프트웨어 스택에서도 널리 쓰이게 되었다. 이번 레슨에서는 DDS의 발행/구독 모델이 어떻게 동작하는지, 그리고 DDS를 다른 미들웨어와 구별 짓는 가장 중요한 특징인 QoS(Quality of Service, 서비스 품질) 정책을 살펴본다.

## 학습 목표

- 발행/구독 패턴이 요청/응답 패턴과 어떻게 다르며, 왜 복잡한 데이터 흐름에 유리한지 설명할 수 있다.
- DDS의 글로벌 데이터 공간(global data space)과 토픽 개념을 이해한다.
- DDS 참여자들이 중앙 서버 없이 서로를 찾는 동적 디스커버리(discovery) 과정을 설명할 수 있다.
- Reliability, Durability, History 같은 핵심 QoS 정책이 각각 어떤 문제를 해결하는지 이해한다.
- 서로 다른 QoS 설정을 가진 발행자와 구독자가 만났을 때 어떤 일이 일어나는지(QoS 호환성) 설명할 수 있다.
- SOME/IP와 DDS가 SOA를 구현하는 서로 다른 접근 방식이라는 점을 비교할 수 있다.

## 발행/구독이란 무엇인가: 모르는 사이에도 통신이 된다

발행/구독 모델을 이해하는 가장 쉬운 비유는 신문 구독이다. 신문사는 독자가 누구인지, 몇 명인지 몰라도 매일 신문을 찍어낸다. 독자는 신문사가 어떤 인쇄소를 쓰는지, 기자가 누구인지 몰라도 구독 신청만 해 두면 매일 신문을 받아볼 수 있다. 신문사(발행자)와 독자(구독자) 사이에는 "신문"이라는 토픽만 있을 뿐, 서로의 존재를 직접 알아야 할 필요가 없다.

DDS는 이 비유를 그대로 소프트웨어에 옮긴다. 발행자는 특정 토픽에 데이터를 쓰기만(write) 하면 되고, 구독자는 그 토픽을 구독(subscribe)하기만 하면 데이터를 받는다(read 또는 콜백으로 수신). DDS는 이렇게 모든 참여자가 공유하는 가상의 공간을 글로벌 데이터 공간(global data space)이라 부르는데, 이는 마치 네트워크 전체가 하나의 커다란 공유 칠판이고, 발행자는 그 칠판의 특정 구역(토픽)에 값을 적고, 구독자는 그 구역을 바라보고 있다가 값이 바뀌면 바로 알아차리는 모델에 가깝다. 실제로는 발행자와 구독자가 유니캐스트나 멀티캐스트로 직접 패킷을 주고받지만, 애플리케이션 코드 입장에서는 "칠판에 쓴다, 칠판을 본다"는 단순한 모델로 통신을 다룰 수 있다.

이 모델이 SOME/IP의 이벤트 구독과 비슷해 보일 수 있지만 중요한 차이가 있다. SOME/IP는 서비스라는 단위 안에 메서드와 이벤트가 묶여 있고, 클라이언트가 특정 서버를 서비스 디스커버리로 찾아 연결을 맺는 과정을 거친다. DDS는 서버라는 개념이 없고, 발행자와 구독자가 모두 동등한 참여자(participant)로서 토픽을 매개로만 연결된다. 발행자가 하나이든 여럿이든, 구독자가 하나이든 여럿이든 DDS의 동작 방식은 동일하다.

## 중앙 서버 없이 서로를 찾는 법: DDS 디스커버리

DDS에는 "서비스를 찾아 주는" 중앙 서버가 없다. 대신 모든 DDS 참여자는 네트워크에 참여하는 순간부터 멀티캐스트로 자신의 존재와 자신이 발행 또는 구독하려는 토픽 정보를 주기적으로 알린다. 이를 받은 다른 참여자들은 서로의 정보를 수집해 "어떤 토픽을 누가 발행하고 누가 구독하는지"에 대한 내부 데이터베이스를 각자 유지한다. 발행자와 구독자가 같은 토픽에 대해 서로를 발견하면, 그 순간부터 둘 사이에 직접적인 데이터 전송 경로가 맺어진다.

이 과정을 보통 SPDP(Simple Participant Discovery Protocol, 참여자 탐색)와 SEDP(Simple Endpoint Discovery Protocol, 엔드포인트 탐색)라는 두 단계로 나눠 설명한다. SPDP는 "이 네트워크에 어떤 참여자들이 있는가"를 먼저 알아내는 단계이고, SEDP는 그 참여자들이 각각 "어떤 토픽에 대해 발행자 또는 구독자 역할을 하는지"를 세부적으로 교환하는 단계다. 이 모든 과정이 자동으로 이루어지기 때문에, 새로운 모듈(예: 새로운 센서 퓨전 알고리즘)을 추가할 때 기존 모듈의 코드나 설정을 전혀 바꾸지 않아도, 새 모듈이 올바른 토픽을 구독하거나 발행하기만 하면 자동으로 기존 네트워크에 합류한다. 이는 SOME/IP의 Offer와 Find가 하는 역할과 목적은 비슷하지만, DDS는 서버와 클라이언트의 구분 없이 발행자와 구독자라는 더 대칭적인 역할로 이를 수행한다는 점이 다르다.

## 토픽의 데이터 타입과 키: 같은 토픽, 여러 인스턴스

DDS에서 발행자와 구독자가 데이터를 주고받으려면 먼저 "이 토픽에 어떤 모양의 데이터가 실리는지"를 양쪽이 똑같이 알고 있어야 한다. 이를 정의하는 수단이 IDL(Interface Definition Language, 인터페이스 정의 언어)이다. 예를 들어 레이더가 감지한 물체 하나의 정보를 담는 토픽이라면, 다음과 같이 데이터 구조를 정의할 수 있다.

```
struct ObstacleInfo {
    long   object_id;   // @key
    double distance_m;
    double relative_speed_mps;
};
```

여기서 object_id 필드에 붙은 주석 @key는 이 필드가 키(key)라는 것을 나타낸다. 키는 "같은 토픽 안에서 서로 다른 개체를 구분하는 식별자" 역할을 한다. 예를 들어 레이더가 동시에 세 개의 물체를 감지하고 있다면, ObstacleInfo라는 하나의 토픽 안에 object_id가 1, 2, 3인 세 개의 서로 다른 인스턴스(instance)가 동시에 존재하는 것으로 다뤄진다. 구독자는 object_id별로 각 인스턴스의 최신 값을 따로 추적할 수 있고, 어떤 물체가 더 이상 감지되지 않으면 발행자가 그 인스턴스를 "소멸(dispose)"했다고 알릴 수도 있다. 이 키 개념이 있기 때문에, 토픽 하나로 "같은 종류지만 서로 다른 여러 개체"의 데이터를 자연스럽게 표현할 수 있다. 만약 키가 없다면 물체마다 별도의 토픽을 만들어야 하는데, 물체 수가 매번 바뀌는 센서 데이터에서는 이런 설계가 현실적이지 않다.

## QoS: DDS를 다른 미들웨어와 구분 짓는 핵심

DDS가 다른 발행/구독 미들웨어와 가장 크게 구별되는 지점은 QoS(Quality of Service, 서비스 품질) 정책의 풍부함이다. 토픽 하나를 주고받을 때, "이 데이터가 꼭 도착해야 하는지", "늦게 구독한 쪽에게도 과거 값을 줄지", "과거 몇 개까지 기억해 둘지" 같은 세부 동작을 발행자와 구독자가 각각 선언할 수 있다. 대표적인 QoS 정책 몇 가지를 살펴보자.

Reliability(신뢰성) QoS는 데이터 손실을 허용할지를 정한다. BEST_EFFORT로 설정하면 UDP처럼 손실을 허용하되 빠르고 가벼운 전송을 하고, RELIABLE로 설정하면 손실된 데이터를 재전송해 모든 데이터가 도착하는 것을 보장한다. 차량 속도처럼 다음 값이 금방 또 오는 데이터는 BEST_EFFORT로 설정해 약간의 손실을 감수하더라도 지연을 줄이는 쪽을 택할 수 있고, 진단 로그나 설정값처럼 한 번이라도 빠지면 안 되는 데이터는 RELIABLE로 설정한다. RELIABLE은 내부적으로 수신 확인(ACK)과 재전송 요청(NACK) 메시지를 추가로 주고받기 때문에, 같은 데이터를 보내더라도 BEST_EFFORT보다 네트워크 트래픽과 지연이 조금 더 늘어난다는 점도 함께 고려해야 한다. 즉 Reliability를 무조건 RELIABLE로 높게 설정하는 것이 항상 좋은 선택은 아니며, 데이터의 성격에 맞춰 손실 허용 여부와 오버헤드 사이의 균형을 맞추는 것이 QoS 설계의 핵심이다.

Durability(지속성) QoS는 "구독자가 데이터가 발행된 이후에 늦게 합류했을 때, 과거에 발행된 데이터를 받을 수 있는가"를 정한다. VOLATILE로 설정하면 구독을 시작한 시점 이후에 발행된 데이터만 받고, TRANSIENT_LOCAL로 설정하면 발행자가 가지고 있는 마지막 값(들)을 늦게 구독한 쪽에도 전달한다. 예를 들어 차량의 현재 설정 상태처럼 "항상 최신 값을 알고 있어야 하는" 토픽은 TRANSIENT_LOCAL로 설정해, 모듈이 재시작되어 다시 구독을 시작해도 가장 최근 값을 즉시 받을 수 있게 한다.

History(이력) QoS는 발행자나 구독자가 토픽의 과거 값을 몇 개까지 저장해 둘지를 정한다. KEEP_LAST(depth=N)로 설정하면 최근 N개만 보관하고 더 오래된 값은 버리며, KEEP_ALL로 설정하면 리소스가 허용하는 한 모든 값을 보관한다. 빠르게 갱신되는 센서 값은 보통 KEEP_LAST(depth=1)로 설정해 항상 가장 최근 값만 의미 있게 유지하고, 이벤트 로그처럼 하나도 놓치면 안 되는 데이터는 더 큰 depth나 KEEP_ALL을 쓴다.

```
// 발행자 QoS 설정 예시 (개념적인 의사코드)
TopicQos qos;
qos.reliability = RELIABLE;
qos.durability  = TRANSIENT_LOCAL;
qos.history     = KEEP_LAST(depth = 5);
publisher.create_datawriter(topic, qos);
```

<details><summary><b>심화: 요청/오퍼 호환성 모델 — QoS가 다르면 왜 연결이 거부되는가</b></summary>

DDS는 발행자와 구독자가 서로 다른 QoS를 선언했을 때 무조건 연결을 맺어 주지 않는다. 대신 요청/오퍼(Request/Offered) 호환성 모델이라는 규칙을 둔다. 구독자는 "나는 최소한 이 정도의 서비스 품질을 요구한다(requested)"고 선언하고, 발행자는 "나는 이 정도의 서비스 품질을 제공한다(offered)"고 선언한다. 발행자가 제공하는 품질이 구독자가 요구하는 품질과 같거나 그보다 더 좋을 때만 둘 사이의 연결(매칭, matching)이 성립한다.

예를 들어 구독자가 Reliability를 RELIABLE로 요구했는데 발행자가 BEST_EFFORT로만 제공한다면, 발행자가 제공하는 품질이 구독자가 요구하는 최소 수준에 미치지 못하므로 둘은 매칭되지 않는다. 반대로 발행자가 RELIABLE로 제공하는데 구독자가 BEST_EFFORT만 요구한다면, 제공되는 품질이 요구 수준보다 높으므로 매칭이 성립한다. 이 규칙이 있는 이유는 명확하다. 만약 QoS가 호환되지 않는데도 조용히 연결이 이루어진다면, 구독자는 자신이 요구한 신뢰성을 보장받지 못하면서도 그 사실을 전혀 알지 못한 채 동작하게 된다. 이는 안전이 중요한 차량 소프트웨어에서는 받아들이기 어려운 조용한 실패(silent failure)다. DDS는 매칭되지 않는 QoS 쌍에 대해 명시적으로 "연결되지 않았다"는 상태를 애플리케이션에 알려 주어, 이런 조용한 실패를 방지한다.

</details>

<details><summary><b>심화: DDS와 ROS 2의 관계</b></summary>

ROS 2(Robot Operating System 2)는 로봇과 자율주행 소프트웨어 개발에서 널리 쓰이는 소프트웨어 프레임워크인데, 그 통신 계층의 기본 구현으로 DDS를 채택했다. ROS 2의 토픽, 퍼블리셔, 서브스크라이버 개념은 사실상 DDS의 발행/구독 모델을 그대로 감싸서 쓰기 쉬운 API로 제공한 것이다. ROS 2가 DDS를 선택한 이유도 이번 레슨에서 다룬 특징들과 직결된다. 자율주행 소프트웨어는 인식, 센서 퓨전, 경로 계획, 제어처럼 수십 개의 노드가 복잡하게 데이터를 주고받는데, 이런 그래프형 데이터 흐름은 발행/구독 모델과 QoS 기반의 세밀한 전송 제어가 딱 맞아떨어지는 사용 사례였기 때문이다.

다만 ROS 2가 자동차 양산 소프트웨어의 유일한 답은 아니다. AUTOSAR 기반 양산 ECU 소프트웨어 스택에서는 SOME/IP가 여전히 표준 통신 미들웨어로 넓게 쓰이고, DDS는 자율주행처럼 데이터 흐름이 매우 유동적이고 복잡한 영역, 그리고 연구·개발 단계의 로봇 소프트웨어 스택에서 더 두드러지게 쓰인다. 최근에는 AUTOSAR Adaptive Platform에서도 DDS를 통신 백엔드의 선택지로 지원하는 등, 두 미들웨어가 서로 배타적이지 않고 영역에 따라 함께 쓰이는 방향으로 발전하고 있다.

</details>

**확인 문제.** 구독자가 Durability를 TRANSIENT_LOCAL로 요구했는데, 발행자가 VOLATILE로만 제공하고 있다. 이 둘은 매칭되는가? 이유를 설명하라.

<details><summary>답 보기</summary>

매칭되지 않는다. 요청/오퍼 호환성 모델에서는 발행자가 제공하는 품질이 구독자가 요구하는 품질과 같거나 그보다 더 강해야 한다. TRANSIENT_LOCAL은 늦게 구독해도 과거 값을 받을 수 있다는 더 강한 보장이고, VOLATILE은 그런 보장이 없는 더 약한 수준이다. 구독자가 TRANSIENT_LOCAL을 요구했는데 발행자가 그보다 약한 VOLATILE만 제공한다면 요구 수준을 만족시키지 못하므로, DDS는 이 둘을 연결하지 않는다.

</details>

**확인 문제.** 어떤 토픽에 빠르게 갱신되는 레이더 거리 값을 흘려보내려 한다. 값이 1 ms마다 갱신되고, 구독자는 항상 가장 최근 값만 필요로 한다. 이 토픽에는 History QoS를 어떻게 설정하는 것이 적합한가?

<details><summary>답 보기</summary>

KEEP_LAST(depth=1)로 설정하는 것이 적합하다. 구독자가 항상 가장 최근 값만 필요로 하므로 과거 값을 여러 개 쌓아 둘 필요가 없고, depth를 1로 두면 메모리와 전송 오버헤드를 최소화하면서도 항상 최신 값만 유지할 수 있다. 만약 과거 몇 개의 값으로 변화 추세를 계산해야 하는 상황이라면 depth를 그 개수만큼 늘려야 하지만, 이 문제처럼 "항상 최신 값만" 필요한 경우에는 depth=1이 가장 효율적이다.

</details>

## 정리

- 발행/구독 패턴은 발행자와 구독자가 서로의 존재를 몰라도 토픽을 매개로 데이터를 주고받을 수 있게 하며, 복잡하고 유동적인 데이터 흐름에 유리하다.
- DDS는 글로벌 데이터 공간이라는 모델 위에서 모든 참여자가 동등하게 토픽을 발행하거나 구독한다.
- DDS 참여자들은 SPDP와 SEDP라는 동적 디스커버리 과정을 통해 중앙 서버 없이 서로를 자동으로 찾아 연결한다.
- Reliability, Durability, History 같은 QoS 정책은 데이터 손실 허용 여부, 늦은 구독자에 대한 과거 값 제공 여부, 보관할 과거 값의 개수를 세밀하게 제어한다.
- 요청/오퍼 호환성 모델은 발행자의 제공 품질이 구독자의 요구 품질보다 낮으면 연결을 거부해 조용한 실패를 방지한다.
- SOME/IP는 서비스 단위의 요청/응답과 서버 중심 디스커버리에 강점이 있고, DDS는 대칭적인 발행/구독과 세밀한 QoS 제어에 강점이 있어, 두 미들웨어는 서로 경쟁한다기보다 영역에 따라 함께 쓰인다.

지금까지 통신 미들웨어 영역에서 SOME/IP와 DDS를 차례로 살펴보며, "서비스를 어떻게 찾고 데이터를 어떻게 흘려보내는가"에 대한 두 가지 다른 답을 확인했다. 두 미들웨어 모두 결국 CAN의 고정 배선 방식이 소프트웨어 중심 차량의 유연성 요구를 감당하지 못한다는 같은 문제의식에서 출발했지만, 요청/응답 중심으로 풀지, 발행/구독과 QoS 중심으로 풀지에 대한 선택이 다르다. 이어지는 진단 영역에서는 이런 통신 네트워크 위에서 차량의 상태를 점검하고 오류를 진단하는 UDS를 다루게 되는데, 이때도 지금 배운 "데이터가 어떻게 흘러가는가"에 대한 감각이 계속 쓰인다.

# MCU 구조 · 메모리

지금까지 두 가지를 따로 배웠습니다. C 레슨에서는 `*gpio_data_reg = 1;`이라는 코드로 레지스터에 값을 쓰는 법을, 디지털 논리 레슨에서는 그 값이 결국 플립플롭에 저장되고 게이트들을 거쳐 물리적 신호가 된다는 것을 배웠습니다. 그런데 "CPU가 어떻게 이 코드를 실행하는가"와 "수십 개의 서로 다른 레지스터가 어떻게 하나의 주소 공간 안에 깔끔하게 정리되어 있는가"는 아직 설명하지 않았습니다. 이 레슨은 그 빈틈을 채웁니다. 하나의 작은 칩 안에 CPU와 메모리와 각종 주변장치(peripheral)가 모두 들어 있는 마이크로컨트롤러(MCU, Microcontroller Unit)가 전체적으로 어떻게 구성되어 있는지를 다룹니다.

일반 PC는 CPU, RAM, 하드디스크, 그래픽카드가 각각 독립된 부품으로 분리되어 메인보드 위에서 선으로 연결됩니다. 반면 자동차 ECU에 들어가는 MCU는 CPU 코어, 수백 킬로바이트의 플래시 메모리, 수십 킬로바이트의 RAM, GPIO·타이머·UART·CAN·ADC 같은 주변장치가 모두 하나의 실리콘 조각 안에 통째로 들어 있습니다. 이렇게 하나의 칩에 컴퓨터의 핵심 구성요소를 모두 집적한 것을 SoC(System on Chip)에 가까운 구조라고 부르기도 합니다. 이런 구조를 이해하지 못하면 "왜 똑같은 포인터 문법으로 메모리도 읽고 하드웨어 레지스터도 읽는지", "인터럽트가 걸리면 CPU가 정확히 무슨 일을 하는지" 같은 질문에 답할 수 없고, 데이터시트(datasheet, 칩 제조사가 제공하는 상세 규격 문서)를 읽어도 각 항목이 왜 거기 있는지 감이 잡히지 않습니다.

이 레슨은 디지털 논리 레슨에서 배운 게이트와 플립플롭, 클럭 개념을 바탕으로, CPU 내부의 명령어 실행 흐름, 메모리 맵(memory map)이라는 조직 원리, 그리고 주변장치와 인터럽트(interrupt)까지를 하나의 그림으로 연결합니다.

## 학습 목표

- CPU가 명령어를 가져오고(fetch) 해석하고(decode) 실행하는(execute) 기본 사이클을 설명할 수 있다.
- 메모리 맵(memory map)이 플래시, RAM, 레지스터를 하나의 주소 공간에 조직하는 원리와 메모리 매핑 입출력(MMIO)을 이해한다.
- 버스와 클럭 트리가 CPU와 주변장치를 어떻게 연결하고 동작시키는지 개략적으로 설명할 수 있다.
- GPIO, 타이머, UART 같은 대표적인 주변장치가 레지스터를 통해 어떻게 제어되는지 설명할 수 있다.
- 인터럽트가 발생했을 때 CPU가 수행하는 동작과, 인터럽트 우선순위가 왜 필요한지 설명할 수 있다.

## CPU 내부: 명령어를 가져오고, 해석하고, 실행한다

CPU(중앙처리장치)는 결국 디지털 논리 레슨에서 배운 조합 회로와 순차 회로의 거대한 집합입니다. 내부에는 몇 가지 핵심 구성요소가 있습니다.

- 레지스터 파일(register file): CPU가 즉시 꺼내 쓸 수 있는 아주 빠른 소수의 저장 공간입니다. ARM Cortex-M 같은 임베디드 CPU는 보통 R0부터 R15까지 16개 정도의 범용 레지스터를 가집니다.
- 프로그램 카운터(PC, Program Counter): "다음에 실행할 명령어가 메모리의 어느 번지에 있는가"를 담고 있는 특수 레지스터입니다.
- ALU(Arithmetic Logic Unit): 더하기, 빼기, 비트 연산처럼 실제 계산을 수행하는 조합 논리 회로입니다. C에서 쓴 `+`, `&`, `<<` 연산이 결국 이 ALU 안의 게이트들을 거칩니다.

CPU는 클럭에 맞춰 다음 세 단계를 끊임없이 반복합니다. 먼저 PC가 가리키는 번지에서 명령어를 메모리로부터 읽어옵니다(fetch). 그 명령어가 "두 레지스터를 더하라"인지 "메모리에서 값을 읽어라"인지 해석합니다(decode). 그리고 실제로 그 동작을 수행합니다(execute). 이 세 단계가 끝나면 PC는 보통 다음 명령어를 가리키도록 자동으로 증가하며, 이 사이클이 1초에 수천만에서 수억 번 반복됩니다. C 코드 한 줄, 예를 들어 `rpm = rpm + 1;`은 컴파일되면 "레지스터에 rpm 값을 읽어 와라, 1을 더해라, 결과를 메모리에 다시 써라" 같은 여러 개의 짧은 명령어로 쪼개져서, 이 fetch-decode-execute 사이클을 여러 번 거쳐 실행됩니다.

## 메모리 맵: 하나의 주소 공간에 모든 것을 배치하기

C 레슨에서 "메모리의 어느 번지가 사실은 GPIO 레지스터다"라는 이야기를 했습니다. 이게 어떻게 가능한지를 설명하는 개념이 메모리 맵(memory map)입니다. MCU는 CPU가 접근할 수 있는 전체 주소 공간(예를 들어 32비트 주소라면 0번지부터 0xFFFFFFFF번지까지)을 미리 몇 개의 구간으로 나누어, 각 구간을 플래시 메모리, SRAM, 혹은 특정 주변장치의 레지스터 묶음에 할당해 둡니다. 예를 들어 다음과 같은 식입니다(실제 번지는 제조사와 모델마다 다릅니다).

- 0x0000_0000 ~ 0x0007_FFFF: 플래시 메모리 (프로그램 코드가 저장되는 영역)
- 0x2000_0000 ~ 0x2000_FFFF: SRAM (변수, 스택이 올라가는 영역)
- 0x4002_0000 ~ 0x4002_03FF: GPIO 포트 A 레지스터
- 0x4001_0000 ~ 0x4001_03FF: 타이머 레지스터

디지털 논리 레슨에서 배운 주소 디코더가 바로 이 구간 구분을 물리적으로 실현하는 회로입니다. CPU가 "0x4002_0000번지에 쓰기를 한다"는 신호를 버스에 실으면, 주소 디코더가 그 번지가 GPIO 포트 A의 영역에 속한다는 것을 판단해서 GPIO 모듈로 가는 선택선만 활성화합니다. 그 결과 CPU 입장에서는 RAM에 값을 쓰는 것과 GPIO 레지스터에 값을 쓰는 것이 완전히 같은 명령어, 같은 포인터 문법으로 처리됩니다. 이렇게 하드웨어 레지스터를 메모리 주소의 일부처럼 다루는 방식을 메모리 매핑 입출력(MMIO, Memory-Mapped I/O)이라고 부릅니다. 앞서 C 레슨에서 본 `volatile uint32_t *gpio_data_reg = (volatile uint32_t *)0x40020014;` 같은 코드가 가능했던 근본적인 이유가 바로 이 메모리 맵 구조입니다.

프로그램이 시작될 때, 코드(플래시 영역)는 변하지 않고 그대로 있지만, 전역 변수와 스택은 SRAM 영역에 배치됩니다. 링커(linker)라는 빌드 도구가 각 심볼(함수, 변수)을 메모리 맵의 어느 구간에 배치할지를 결정하는 링커 스크립트(linker script)를 사용합니다.

## 버스와 클럭 트리: CPU와 주변장치를 잇는 길

CPU, 메모리, 여러 주변장치가 서로 데이터를 주고받으려면 이들을 연결하는 통로가 필요합니다. 이 통로를 버스(bus)라고 부릅니다. Cortex-M 기반 MCU는 흔히 AHB(Advanced High-performance Bus)라는 빠른 버스로 CPU와 메모리, 고속 주변장치를 연결하고, APB(Advanced Peripheral Bus)라는 상대적으로 느리지만 전력을 적게 쓰는 버스로 GPIO, UART 같은 저속 주변장치를 연결하는 계층적인 버스 구조를 씁니다. 모든 주변장치가 다 같은 속도로 동작할 필요가 없기 때문에, 빠른 것과 느린 것을 분리해서 전력과 설계 복잡도를 줄이는 것입니다.

디지털 논리 레슨에서 배운 클럭은 MCU 전체에서도 핵심 역할을 합니다. 다만 MCU 내부의 모든 블록이 똑같은 속도로 돌 필요는 없습니다. CPU 코어는 80MHz로 빠르게 돌지만, 특정 저속 통신 주변장치는 전력을 아끼기 위해 1MHz로만 돌아도 충분할 수 있습니다. 그래서 MCU 내부에는 클럭 트리(clock tree)라는 구조가 있어서, 하나의 기준 발진기(오실레이터) 신호를 여러 배 또는 여러 분의 1로 조정하는 회로(PLL, 분주기)를 거쳐, 각 블록에 필요한 만큼의 클럭을 따로 공급합니다. 소프트웨어에서 "타이머의 클럭 소스를 설정한다"거나 "저전력 모드에서 특정 주변장치의 클럭을 끈다"는 작업이 바로 이 클럭 트리를 제어하는 것입니다. 쓰지 않는 주변장치의 클럭을 꺼 두면 그만큼 전력 소비를 줄일 수 있어, 배터리로 동작하는 모듈이나 발열이 민감한 ECU에서 중요하게 다뤄집니다.

## 주변장치: 레지스터로 말을 거는 작은 하드웨어 전문가들

CPU 혼자서는 정해진 전압을 핀에 걸거나, 정확한 시간 간격을 재거나, 시리얼 통신 프로토콜의 타이밍을 맞추는 일을 모두 소프트웨어로 처리하기에는 너무 바쁘고 느립니다. 그래서 MCU는 이런 특화된 작업을 전담하는 작은 하드웨어 회로들을 함께 내장하는데, 이를 주변장치(peripheral)라고 부릅니다. 대표적인 주변장치는 다음과 같습니다.

- GPIO(General Purpose Input/Output): 핀 하나를 입력 또는 출력으로 쓰도록 설정하고, 그 핀의 전압 상태를 읽거나 쓰는 모듈.
- 타이머(Timer): 디지털 논리 레슨에서 배운 카운터 회로를 내장해서, 일정 시간이 지나면 인터럽트를 발생시키거나 PWM(펄스 폭 변조) 신호를 만들어내는 모듈.
- UART: 시리얼 통신 프로토콜의 비트 단위 타이밍을 하드웨어가 자동으로 처리해 주는 모듈.
- ADC(Analog-to-Digital Converter): 센서가 보내는 연속적인 전압값을 디지털 숫자로 바꿔주는 모듈.
- CAN 컨트롤러: 차량 네트워크 프로토콜의 메시지 조립, 중재, 오류 검출을 하드웨어가 처리해 주는 모듈.

각 주변장치는 앞서 C 레슨에서 본 것처럼 몇 개의 레지스터 묶음으로 CPU에게 자신을 드러냅니다. CPU는 이 레지스터에 값을 쓰거나 읽는 것만으로 주변장치를 설정하고 제어하며, 주변장치 내부에서 실제로 어떤 회로가 동작하는지는 CPU가 전혀 몰라도 됩니다. 데이터시트의 "레지스터 맵(register map)" 챕터가 바로 이 레지스터들의 의미를 비트 단위로 설명하는 부분이며, 임베디드 개발의 많은 작업이 결국 "데이터시트를 읽고 올바른 레지스터에 올바른 값을 써넣는 일"로 귀결됩니다.

## 인터럽트: CPU가 하던 일을 멈추고 끼어드는 순간

버튼이 눌리거나, UART로 데이터가 도착하거나, 타이머가 설정한 시간에 도달하는 사건은 CPU가 지금 무엇을 하고 있는지와 무관하게 아무 때나 일어날 수 있습니다. CPU가 계속 "혹시 버튼이 눌렸나, 혹시 데이터가 왔나"를 반복해서 확인하는 방식(폴링, polling)은 CPU 시간을 낭비하고 반응이 늦어질 수 있습니다. 그 대신 주변장치가 "사건이 일어났다"는 것을 CPU에게 직접 알려주는 방식이 인터럽트(interrupt)입니다.

인터럽트가 발생하면 CPU는 지금 실행하던 명령어 흐름을 멈추고, 현재 레지스터 상태를 스택에 저장한 뒤, 그 인터럽트에 해당하는 특별한 함수(인터럽트 서비스 루틴, ISR)로 점프해서 실행합니다. ISR이 끝나면 저장해 두었던 레지스터 상태를 복원하고, 원래 하던 작업을 이어서 계속합니다. ARM Cortex-M 계열 MCU는 NVIC(Nested Vectored Interrupt Controller)라는 전용 하드웨어가 "지금 어떤 인터럽트가 걸렸는지, 어느 것이 더 우선순위가 높은지, ISR의 시작 주소(벡터)가 어디인지"를 관리합니다. 예를 들어 제동 관련 센서의 인터럽트는 인포테인먼트 화면 갱신 인터럽트보다 우선순위가 높게 설정되어, 두 인터럽트가 동시에 걸려도 CPU가 더 중요한 쪽을 먼저 처리하게 만들 수 있습니다. 이 인터럽트 우선순위 설계가 바로 ds-algo 레슨에서 다룬 원형 버퍼가 ISR과 메인 루프 사이에서 쓰이는 이유, 그리고 ISR을 가능한 짧게 작성해야 하는 이유와 직접 연결됩니다.

<details><summary><b>심화: 하버드 구조와 폰 노이만 구조</b></summary>

일반 PC의 CPU는 명령어와 데이터를 같은 메모리 공간에서 가져오는 폰 노이만 구조(von Neumann architecture)를 쓰지만, 많은 임베디드 MCU는 명령어를 읽어오는 버스와 데이터를 읽고 쓰는 버스를 물리적으로 분리한 하버드 구조(Harvard architecture, 또는 변형인 수정 하버드 구조)를 채택한다. 이렇게 분리하면 CPU가 다음 명령어를 가져오는 동시에 현재 명령어가 쓸 데이터도 동시에 읽어올 수 있어서 처리 속도가 빨라진다. ARM Cortex-M 계열도 수정 하버드 구조에 가까운 버스 배치를 쓴다. 다만 소프트웨어 개발자 입장에서는 플래시(명령어)와 SRAM(데이터)이 메모리 맵 안에서 서로 다른 구간에 있다는 사실만 알면 충분하고, 버스가 물리적으로 몇 개로 나뉘어 있는지는 대부분 신경 쓰지 않아도 된다.

</details>

<details><summary><b>심화: 플래시 대기 상태와 타이밍 예측 가능성</b></summary>

CPU 클럭 속도가 플래시 메모리의 읽기 속도보다 빠른 경우, CPU가 매 클럭마다 명령어를 플래시에서 즉시 읽어올 수 없는 상황이 생긴다. 이때는 CPU가 몇 클럭을 기다려야 하는 대기 상태(wait state)를 추가해서 타이밍을 맞춘다. 데스크톱 CPU는 이런 지연을 캐시(cache)로 가려서 평균 속도를 높이지만, 캐시는 "이번에 캐시에 있었는지 없었는지"에 따라 실행 시간이 들쭉날쭉해지는 효과를 낳는다. 안전이 중요한 자동차 소프트웨어는 ds-algo 레슨에서 다룬 최악 실행 시간(WCET) 예측 가능성을 중시하기 때문에, 일부 안전 필수 MCU는 캐시를 비활성화하거나 매우 제한적으로만 사용하고, 대신 플래시 접근 지연을 고정된 대기 상태로 명시적으로 관리하는 방식을 선호한다.

</details>

**확인 문제.** CPU가 `*gpio_data_reg = 1;`을 실행할 때, 이 코드가 RAM의 평범한 변수에 값을 쓰는 것과 문법적으로 완전히 똑같이 보이는 이유를 메모리 맵 관점에서 설명하라.

<details><summary>답 보기</summary>

MCU는 CPU가 접근 가능한 전체 주소 공간을 미리 구간별로 나누어, 어떤 구간은 SRAM에, 어떤 구간은 특정 주변장치의 레지스터에 할당해 둔다(메모리 맵). CPU의 "메모리에 쓰기" 명령어는 대상이 SRAM인지 레지스터인지 구분하지 않고 그냥 "이 번지에 이 값을 써라"라는 동일한 동작만 수행하며, 실제로 그 번지가 어느 하드웨어 모듈로 연결되는지는 버스에 연결된 주소 디코더 회로가 물리적으로 결정한다. 그래서 `gpio_data_reg`가 가리키는 주소가 GPIO 모듈 영역에 속해 있다면, 똑같은 포인터 대입 문법이 실제로는 GPIO 핀의 전압을 바꾸는 동작으로 이어지는 것이다. 이것이 메모리 매핑 입출력(MMIO)의 핵심이다.

</details>

**확인 문제.** 인터럽트 서비스 루틴(ISR)을 가능한 짧고 빠르게 작성해야 한다고 흔히 강조된다. 그 이유를 CPU 동작 관점에서 설명하라.

<details><summary>답 보기</summary>

인터럽트가 발생하면 CPU는 하던 작업을 멈추고 ISR로 점프하며, ISR이 끝나기 전까지는 원래 하던 작업으로 돌아갈 수 없다. 만약 ISR이 오래 걸리면, 그 시간 동안 다른 긴급한 작업(심지어 더 중요한 다른 인터럽트일 수도 있다. 우선순위에 따라 선점이 가능한 경우도 있지만 설계에 따라 제한적이다)이 지연될 수 있고, 이는 ds-algo 레슨에서 다룬 최악 실행 시간(WCET) 보장을 어렵게 만든다. 그래서 실무에서는 ISR 안에서는 받은 데이터를 원형 버퍼 같은 자료구조에 빠르게 옮겨 담기만 하고, 실제 복잡한 처리는 메인 루프나 더 낮은 우선순위의 작업으로 넘기는 패턴을 흔히 쓴다.

</details>

## 정리

- CPU는 fetch-decode-execute 사이클을 클럭에 맞춰 반복하며, C 코드 한 줄은 이 사이클을 여러 번 거치는 여러 개의 짧은 명령어로 쪼개져 실행된다.
- 메모리 맵은 플래시, SRAM, 각종 주변장치 레지스터를 하나의 주소 공간에 구간별로 배치하며, 이를 통해 레지스터 접근이 평범한 메모리 접근과 같은 문법으로 가능해진다(MMIO).
- 버스와 클럭 트리는 CPU와 주변장치를 연결하고 각 블록에 필요한 속도의 클럭을 분배하며, 전력 관리의 핵심 수단이기도 하다.
- GPIO, 타이머, UART, ADC, CAN 컨트롤러 같은 주변장치는 전담 하드웨어로 특화된 작업을 처리하며, 레지스터 맵을 통해 CPU와 소통한다.
- 인터럽트는 CPU가 사건이 일어난 순간에만 반응하도록 해 주며, 우선순위와 ISR의 길이는 실시간성 보장에 직접적인 영향을 준다.

MCU 구조를 이해하면, 데이터시트의 레지스터 설명이 더 이상 외계어처럼 느껴지지 않는다. CPU, 메모리 맵, 버스, 주변장치, 인터럽트라는 다섯 가지 축은 이후 RTOS, 통신 프로토콜, 실제 드라이버 작성 레슨 전체에서 반복적으로 등장하는 뼈대다.
